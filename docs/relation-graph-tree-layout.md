# 关系图：继承分层树

## 问题

关系图原本用**力导向布局**（手写弹簧 + 斥力 + rAF 余温）。在 DocMind 自己的项目上实测：

```
1485 节点 / 1245 继承边 / 8 调用边 / 0 挂载边
```

继承边占 **99.4%**，而且它们本来是**树**（继承森林），不是网。

力导向画一棵树的结果：1245 条弹簧互相拉扯，节点挤成一团毛球 —— 看不出"谁继承谁"，
也看不出哪块代码是核心。继承深度最多只有 3 层，结构本该一眼可读。

另外三个问题：

- **规模无上限**：后端 `GET /api/fs/relation-graph` 全量返回，1485 个节点全进画布。
- **大扇出**：`unittest.TestCase` 有 **791** 个子类、`pydantic.BaseModel` 有 **121** 个。
  不折叠的话画布高 77,000px，等于没法看。
- **搜索只变暗不减量**：`nodeDim()` 只改 opacity，1485 个节点还在屏幕上。
- **隐藏 bug**：`watch` 只监听四个关系开关，**没监听 `query`** —— 旧实现里搜索只改
  opacity 不改布局，所以没暴露。

## 做法

### 布局引擎（纯函数，可单测）

新增 `frontend/src/workbench/lib/relationTreeLayout.ts`：

- **列 = 继承深度**，行 = tidy tree 槽位（子树连续，父子不交叉）
- **大扇出折叠**：子类数超过阈值（默认 8）→ 收成一张「N 个子类」分组卡，点开才展开
- **折叠的可见性必须自顶向下算**：被折进分组卡的节点，**整棵子树**都看不见了。
  各算各的会出现"悬空分组卡"（卡片在图上，却没有可见的父节点连着它）。
- **零关系节点**（谁也不连、也没人连它，实测 218 个）单独成组，不混进树里 ——
  它们在关系图上本来就是孤立点，混进树里只会让树变形
- **边的主父优先级**：继承 > 挂载 > 调用。树只有一根主父，其余记为**交叉连线**（虚线），
  既不丢信息、又不破坏树的形状
- **成环保护**：Python 的 `class A(B)` / `class B(A)` 在项目里真会出现，
  顺着父链上溯撞回自己就断这条边

### 组件接入

`RelationGraph.vue` 换成树布局：

- 主干边画**折线**（基类右缘 → 中点竖直 → 子类左缘），不横穿整张图
- 交叉连线画虚线 + 弱化，一眼看出"这条不是主干"
- **点分组卡 = 展开/收起**（整棵树重排）
- **搜索只看相关子树**：命中的节点 + 它们的祖先链。树有明确的父子关系，
  "从命中节点往根上回溯"能得到一条有意义的路径 —— 力导向的图里根本没有"祖先"这回事
- 搜索时**自动展开装着命中节点的分组卡**，否则命中节点藏在折叠卡里，等于没搜到
- 补上 `watch(query)`：搜索会改树的形状，不重建就等于搜索没生效

### 两个渲染缺陷

实机验证时抓到的，都不是布局问题：

1. **继承边的文字标签压住卡片**：边图层在节点图层之下，标签被卡片盖住。
   而且继承边在树里有上百条，每条都写 `extends`/`bases` 纯属噪声 ——
   继承关系由颜色 + 图例 + tooltip 表达就够。改为只给少见的挂载/调用边留标签。
2. **卡片文字溢出边框**：`measure()` 按 Segoe UI 9.5px 量宽，但 `.rg-sub` 实际渲染成
   等宽的 Space Mono 11.8px —— **等宽字宽得多**，算出来的卡片宽度偏小，
   `tests/test_realtime_gateway_bridge.py` 这种长路径直接冲出卡片。
   修法：量宽的字体栈必须和渲染时一模一样，字号也用真实令牌值
   （`--fs-sm` 12.9px / `--fs-cap` 11.8px，不是当初估的 12 / 9.5）。

## 效果

实测（DocMind 自己的项目，1485 节点 / 1245 继承边）：

| | 改前 | 改后 |
|---|---|---|
| 默认可见节点 | 1485（全挤在一起） | 83 节点 + 6 分组卡，4 列 |
| 画布 | 毛球，无边界 | 1168 × 3986，分层清晰 |
| 搜索 `RealtimeProvider` | 1485 个节点压暗 | **4 节点 / 3 边**，祖先链完整 |
| 文字溢出卡片 | —（旧的力导向也有，但没人注意） | 0 处（实测 getBoundingClientRect） |
| 卡片重叠 | — | 0 处 |

大扇出折叠后，`unittest.TestCase` 的 791 个子类收成一张卡（点开按需展开），
`pydantic.BaseModel` 的 121 个同理。

## 门禁

`frontend/tests/relationTreeLayout.test.mjs`（20 项）锁的是**关系图必须成立的不变量**，
不是快照：

- 子类必须在基类右边（列 = 继承深度），否则"谁继承谁"读不出来
- 同层节点不能重叠，否则卡片叠在一起等于没布局
- 大扇出必须折叠，否则 791 个子类把画布撑到 7 万像素
- 成环不能死循环（Python 的 `class A(B)` / `class B(A)` 真会出现）
- 折叠的基类不产生悬空分组卡
- 坐标永远有限（父节点行号是小数 —— 子区间中点，早先直接索引整数数组算出 NaN）
- 零关系节点不进树但被计数
- 布局是纯函数，不修改入参
- 实测形状：1485 节点 / 1245 继承边能压进可读画布
