# DocMind 界面精简方案（按改动收益排序）

> 日期：2026-10-19
> 方向：用户明确要求「精简 —— 去掉没必要的功能组件，统一塞到设置界面，保持其他界面干净整洁」。
> 本文是**只读审计 + 方案**，未改动任何产品代码。审计含实机渲染验证（Edge + Playwright，1600×1000 / 1024 / 860 三档宽度，三套皮肤各截一轮）。
> 证据截图见 `.tmp/shots/`（该目录被 gitignore；需要入库时复制到 `docs/screenshots/visual/audit-*.png`，注意**不要**覆盖已有的 `workbench-*.png` / `ask*.png` 基线图）。

---

## 0. 一句话结论

工作台的"功能组件"主要不是多，而是**散、重复、有一半是死的**：11 项低频面板挤在一个「更多」下拉里、同一件事（问 AI / 看显存 / 看花费）有 3～5 个入口、还有一个点进去直接空屏的「开发舱」标签。把这些收进设置 + 删掉死物，**顶栏从 7 个控件降到 4 个、标签页从 4 个降到 3 个、问答页侧栏从 4 块降到 2 块**，主界面立刻干净下来；这一步的成本远低于继续打磨现有界面。

## 2. 实施批次（按「改动收益 ÷ 成本」排序）

### P0 · 死物与重复入口清理（成本 S，收益立竿见影）

## 3. 风险与门禁

- **删入口前先确认没有唯一路径**：例如「分区治理」降级为状态点后，分区图入口要保留；「GPU 监控」并入设置后，"实时看占用"这个诉求仍在设置里可达。
- **P0/P1 每批都要过既有门禁**：`verify_skin_states.mjs`、`verify_skin_token_pairs.mjs`、`verify_visual_regression.mjs`（paper/graphite 像素零差基线）、`verify_workbench_regressions.mjs`。**改层级/字号会动像素基线**，需按脚本注释里的 `--record` 流程重录，不能直接改基线数值。
- **`App.vue` 是双写者交叠文件**（`docs/cockpit-v2-redesign.md:1.2` 明确标注"对方高频提交"）—— 改动前先 `git status`，只加明确路径，**禁 `git add -A`**。
- **门禁本身要跟着改**：`verify_skin_states.mjs:62` 等的是已删插槽；删「开发舱」后门禁状态表里相关用例要清掉，否则门禁变成空跑。

## 4. 审计方法与可信度

- 四路并行只读审计（布局层级 / 配色字体 / 按钮反馈与加载 / 深浅色适配），结论均带 `file:line`。
- 关键论断由我用 Edge + Playwright 实机复核：工作台与问答页 × 三套皮肤 × 三档宽度截图、DOM 计算样式探针、键盘 Tab 焦点序列、点击「开发舱」后的布局塌陷。
- 对比度数字为 WCAG 相对亮度公式现算。
- **未覆盖**：玻璃材质 + 深色皮叠加的实拍观感、真实后端数据下的长列表与长耗时交互（本次用固定夹具工程，无真实数据量）。这些标为"需实机确认"，在对应改动落地时再验。

### 8.2 一处自己引入又修掉的缺陷

批量令牌化时，我的正则 `rgba\(47,\s*111,\s*237,\s*\.?([\d.]+)\)` 把 `.11` 的小数点吃掉、只捕获到 `11`，再 ×100 变成 **1100%**（应为 11%）。`color-mix` 超过 100% 会被 clamp 成纯色 —— 淡边框与淡光晕直接变成实心强调色（聚焦光晕最明显）。

发现方式是跑 `verify_skin_states` 时门禁报"新引入的皮肤泄漏"。修法不靠猜：从 HEAD 原文逐行取出 alpha 重算百分比，共修正 61 处，再逐行核对"当前值 == 原文 alpha×100"全部一致。

**教训**：批量改色值时，正则里"可选的小数点 + 贪婪数字组"这个组合会把 `.11` 读成 `11`。透明度一定要用能区分前导零的写法。

## 10. 编辑器跟皮肤 + 布局密度令牌（2026-10-20）

### 10.1 CodeMirror 6 编辑器主体跟皮肤

**之前的判断是错的**：我曾说"主题固化在 EditorState 里、运行时切皮肤换不掉，所以代码区只能保持浅色"。实测后要更正：

- **主体配色**（底色 / 字色 / 光标 / 选区 / gutter）走的是 `EditorView.theme()` 注入的**普通 CSS 规则**，里面写 `var(--bg-raised)` 之类的变量，浏览器会跟着 `:root` 自动重算 —— **根本不需要重建 EditorState**。
- 只有**语法高亮表**是 JS 对象（CM6 的高亮 class 是混淆名，没法用 CSS 覆盖），才需要换。

所以拆成两半：

| 部分 | 做法 |
| --- | --- |
| 主体配色 | 全部读令牌（`--bg-raised` / `--text` / `--border` / `--bg` / `--text-muted` / `--accent` / `--accent-text`），**自动跟随皮肤** |
| 语法高亮表 | 浅底用 `defaultHighlightStyle`、深底用 `oneDarkHighlightStyle`（`@codemirror/theme-one-dark`，P0 时当死依赖删过，这次装回来），用 **Compartment** 在切肤时 reconfigure |

**明暗判定**读 `skins.css` 新增的 `--skin-dark` 令牌（0/1）—— 以后加深色皮肤只改那一处，不用动 JS。

**多 state 的坑**：工作台每个标签各有一个 `EditorState`，而 Compartment 的 reconfigure 只作用于**被 dispatch 的那个 state**。只换当前这个的话，切到别的标签会露出旧皮肤的高亮表。所以 `CodeView` 在换肤时对**所有** state 各做一次 `rethemeState()`。

**实际收益**：此前编辑器文字是写死的 `#222b38`，深色皮肤下是**深字压深底**（≈1.3:1，整块代码区读不了）；现在跟皮肤走。

**实测**：运行时切到 graphite（不刷新页面）后，语法 token 颜色从 default 的 `#aa1111` 变成 oneDark 的 `#abb2bf / #e06c75 / #98c379` ✅

### 10.2 布局模式密度令牌

`--style-scale`（5 套布局：1 / 1.06 / 0.95 / 0.92 / 0.97）此前**只作用于 body 的 font-size**，而组件字号全写死成 px —— 切「单列专注 / 对半分屏」时密度其实一点没变，**令牌完全空转**。

而且上一节把 931 处字号全换成 `var(--fs-*)` 之后，这些绝对 px 值让空转变得更彻底。

**修法**：让**字阶档位本身**含缩放：

```css
--fs-body: calc(14px * var(--style-scale, 1));
--fs-cap:  calc(11px * var(--style-scale, 1));
/* …共 11 档 */
```

931 处 `var(--fs-*)` 由此**自动跟随布局密度，零组件改动**。

⚠️ 配套必须改：`layout-modes.css` 里那条 `html[data-layout] body { font-size: calc(var(--fs-body) * var(--style-scale)) }` 要去掉重复缩放 —— 否则 focus 的 1.06 会**平方成 1.12**。

**`--style-space-s`**（5 套布局各定义 8/10/6/6/7px，此前全仓 0 消费点）接到两处"小间距"语义最明确的地方：对话台相邻消息的间距（`.cd-msg` 的 margin-bottom）与对话区上内边距（`.cd-body` 的 padding-top）。

**实测**（10 个组合：5 布局 × 1600/1024 两档宽度）：

| 布局 | scale | 字号集 | 溢出 |
| --- | --- | --- | --- |
| fixed | 1 | 11/12/13/14/15/16/22 | 0 |
| focus | 1.06 | 11.66/12.72/13.78/14.84/16.96/23.32 | 0 |
| dock | 0.95 | 10.45/11.4/12.35/13.3/14.25/15.2/20.9 | 0 |
| split | 0.92 | 10.12/11.04/11.96/12.88/13.8/14.72/20.24 | 0 |
| grid | 0.97 | 10.67/11.64/12.61/13.58/14.55/15.52/21.34 | 0 |

split 的最小档 10.12px 偏小，但那是**布局模式自己的设计意图**（原注释："空间被压缩，字号跟着缩"）。

## 13. 产品化改造（2026-10-20）：从"工程样机"到"能上线"

### 13.1 诊断：为什么之前"不像能上线"

实机截图后的结论——问题不在像素细节，在**结构与定位**：

| 现象 | 数据 |
| --- | --- |
| 视口 2/3 是空对话框 | dock 占 620px（62vh），主区只剩 **262px** |
| 首屏主视觉是一句空态提示 | 「这个项目还没启用分区治理」占满主栏、居中大字 |
| 顶栏一排同权重小方块 | 项目/分区/搜索/设置/更多，没有主次 |
| 右栏打开是**一片空白** | `.cd-empty` / `.cd-quick` 这套样式**写了却从未被渲染**（模板里没有引用） |
| 整体像开发工具 | brutalist：墨黑粗边 + 硬偏移阴影 + 孔版纹理 |

问答页反而有产品感（标题 + 示例问题 + 输入区），说明**问题集中在工作台**。

### 13.2 视觉去工程化：zinc 升为默认，brutalist 降为可选

| 改动 | 说明 |
| --- | --- |
| 默认皮肤 paper → **zinc** | 1px 细线 + 6px 圆角 + 零阴影 + 青绿强调；paper（brutalist）保留为可选皮肤，说明改成"印刷海报风，按需选用" |
| 一次性迁移 | 存的是旧默认 paper 且**从没主动选过**的机器自动换到 zinc；主动选过 paper 的（选时写 `docmind.skinLocked` 标记）不动。首帧内联脚本里也做同样的迁移，否则会先按 paper 画一帧再切 —— 白闪 |
| 写死的边宽收编 | 12 处 `border: 2px solid …` / `border-width: 2px` → `var(--edge-w-strong)` / `var(--edge-w-heavy)`（zinc 下自动 1px，paper 下仍 2/3px）。剩下 7 处是滚动条 thumb 的间隔边，保留 |

### 13.3 顶栏重做

- 搜索条从"挤在项目选择器后面"改成**居中伸展**（`flex: 1 1 auto` + `justify-content: center`）。
- 右侧恢复「**问答页**」入口（上一版并进 logo，可发现性太差），「设置」「更多」改成 30×30 纯图标方钮，三者视觉同重。
- 「更多」菜单**改单行**：原来每项是「名称 + 一行说明」两行，9 个项把菜单撑得很高；现在「字形 + 名称」一行，说明挪到 title（悬停才出现），菜单高度减半。分组改名：「分析与视图」/「开发工具与运行」。

### 13.4 结构重排：AI 助手的位置（改过一次，终版回到底部）

**中途试过"右侧常驻栏"（三栏 IDE：文件树 / 内容 / AI），实测下来不成立**：

| 形态 | 主区 | AI 栏 | 回答区宽 | 每行字数 |
| --- | --- | --- | --- | --- |
| 右侧 420px | 892×948 | 420×948 | **389px** | **≈26 字** ❌ |
| 右侧 560px | 752×948 | 560×948 | 529px | ≈36 字 ⚠️ |
| 覆盖式（平时不占位） | 1312×948 | 520×948 | 489px | ≈33 字 ⚠️ |
| **回底部 · 38vh（终版）** | 1312×706 | 全宽 | 680px | **≈47 字** ✅ |

两条理由：

1. **阅读行宽**：中文正文舒适区是 45–75 字/行。420px 的右栏里回答区只剩 389px、每行 26 字，长回答被挤成电报体。
2. **主次**：DocMind 的核心动作是**问**，不是看代码。问答页里聊天是主角，工作台却把它塞进角上、让代码占主位 —— 两个页面对 AI 的定位不一致，工作台也就没了跟 VSCode 的区别。

**终版**：回到底部抽屉，高度从 62vh 降到 **38vh**（380px）：

- 回答区横跨全宽，阅读栏 680px、每行 ≈47 字
- 主区拿到 1312×706（内容区 568px 高）
- 视线自上而下：项目 → 代码 → 对话

## 14. 种子驱动的设计系统（2026-10-20）

### 14.1 动机

前面几轮改下来暴露了一个问题：改界面时最耗人的不是"改哪个色"，而是**凭感觉来回试** ——
改了主色忘了改淡染、改了浅底忘了深底、字号随手写了 11.5px，每一轮都要人肉把所有派生值重算一遍，
而且**没有机制保证下一轮不重犯**。

所以把"设计"变成**可复现的推导**：

    随机种子 → 一整套设计参数（色相/饱和/明度/圆角/描边/阴影/字号/间距）
             → 一份完整皮肤（skins-seed.css）

### 14.2 用法

```bash
python tools/design_seed.py --new-seed   # 随机一个新种子并重新生成皮肤
python tools/design_seed.py              # 用当前种子重新生成（幂等）
python tools/design_seed.py --print      # 只看派生参数，不写文件
```

### 14.3 关键设计：随机选方向，反解明度

色**相/饱和/圆角/阴影/字号/间距**由种子随机决定，但**明度是反解出来的**：

- `ensure_contrast(rgb, bg, target)` 把颜色的明度往目标方向推，直到对底色达到目标对比度；
- 正文类 ≥ 4.5:1（WCAG AA），描边/图形 ≥ 3:1。

所以"随机"不会产出不可用的配色 —— **随机的是风格方向，确定性的是可用性**。

## 15. 令牌归一与种子闭环（R15）

这一轮把"看起来差不多"变成"每一处颜色都有出处"：颜色不再是散落在组件里的字面量，
而是**分层令牌**；同时把一批**深色皮肤下直接隐形**的硬伤挖出来。

### 15.1 令牌分层

新增 `frontend/src/workbench/viz-tokens.css`（只被工作台引用，因为用到它的五个组件
都是工作台的）：

| 档 | 配方 | 用途 | 判据 |
| --- | --- | --- | --- |
| 图形档 55% | `color-mix(in srgb, <色相> 55%, var(--ink))` | 描边 / 填色 / 图例色块 | 1.4.11，3:1 |
| 文字档 36% | 同上但 36% | SVG 里的文字 | 1.4.3，4.5:1 |
| 淡底档 30% | 同上但 30% | 底板压色 | — |

混向 `var(--ink)` 是**双向**的：浅色皮肤压暗、深色皮肤提亮，一个比例两边都达标。
这正是原来写死 `#58a6ff` 做不到的 —— 那个值在纸底上只有 2.2:1，在石墨底上又太亮。

原散在 `RelationGraph` / `SymbolMap` / `UnityGraph` / `SceneCanvas` 里的
**38 处手写配方**（同一个 `color-mix(... 55%, var(--ink))` 抄了 38 遍）全部收进这一处。

> 顺带纠正一条**过时认知**：关系图里原有注释说"SVG 呈现属性里写 var() 不解析，会静默
> 回落到黑色"。实测 Chromium 下 `fill="var(--x)"` 与 `stroke="var(--x)"` 都能正确解析
> （`color-mix()` 在呈现属性里也能解析）。注释已按实测更正 —— 但实现仍统一走 `style=`
> 属性，因为那是**明确**的写法，不依赖浏览器的宽容度。

### 15.2 修掉的真缺陷

| 缺陷 | 位置 | 症状 |
| --- | --- | --- |
| DAG 节点文字写死深色 | `RegionMapDialog.vue` | 面板底是 `--bg-raised`，深色皮肤下 `#222b38` 压深底 = **隐形** |
| 语义状态色写死 | 11 个面板文件 43 处 | `#c23a40`（深红）压深色皮肤 = **隐形**；`--danger` 每套皮肤都重定义过，组件却不用 |
| 死令牌 | `--amber-deep` 7 处、`--font-sans` 19 处、`--text-dim` 5 处、`--font-base` 1 处 | 从未定义 → `color: var(--x)` 整条失效 → 回落继承值。**它们一直"碰巧"看得清，但没有任何一处跟着皮肤走** |
| **透明度放大 10 倍** | `SymbolOutline.vue` 类卡底、`style.css` 加载光晕 | `rgba(47,111,237,.06)` 被写成 `60%` → 淡底变实心强调色 |

### 15.3 一个自己踩的坑：alpha 放大 10 倍

批量把 `rgba(r,g,b,.06)` 改写成 `color-mix(... NN%, transparent)` 时，如果用
"可选小数点 + 贪婪数字组"的正则取 alpha，`.06` 会被读成 `6` 再乘 10 → 60%；
`.13` 读成 `13` 正好对。于是同一条规则里一个错一个对，肉眼只看出"颜色变怪"。

**扫描器自己也栽了一次**：第一版正则按 `color-mix(in srgb, <色>, <NN>%, ...)` 写，
而 `color-mix` 的百分比是跟在**颜色后面**、逗号**之前**的 —— 正则从未匹配上，
扫出来的"未发现"是假的。改成 `color-mix(in srgb, <色> NN%, <色2>)` 并按
**diff hunk 内**配对（按行号或按字节位置就近配对都会产生大量假阳性）之后，
精确命中 2 处真缺陷。

脚本留在 `.tmp/scan-alpha-10x.mjs`，判据是脚本签名 `新百分比 = 旧 alpha × 1000`。

### 15.4 换种子闭环实测

把种子从 **569161024**（深底 / 暖红 / 12px 圆角 / 零阴影）换成
**344284156**（**浅底** / 梅红 / 14px 圆角 / **2px 粗边** / **硬阴影** / 15px 正文 / 密度 1.05），
跑完整条闭环。这一步的价值在于：新种子是**浅色**的，把"深色皮肤专属"的假设全部掀翻了。

闭环暴露了 4 个问题，每一个都是真的：

1. **生成器的解算基准面取错了**。浅底分支把文字色对 `raised`（更亮的板面）解算，
   而深色文字压**更暗**的 `--bg` 上对比度更低 → 种子的 `--text-faint` 压 `--bg` 只有 4.41:1。
   改成对 `bg` 解算（深底分支本来就对，那边最坏面恰好是 `raised`）。
2. **同色相淡底上的字色**（15.2 那条）在新种子上暴露成 14 处 → 引出 `--*-deep` 一族。
3. **`--accent-2` 没有"深档"** → 补 `--accent-2-deep`。
4. **门禁自己把种子写死成深色皮肤**：`EXPECT_WEAK_MUTATED` 是一张按皮肤名索引的
   硬编码表，种子换成浅色后，"ink 全改白"这一变异打不掉任何一对，期望值却还写着 5。
   改成**解析算**：哪几对的填色承不住白字（用皮肤自己的取值算，不是跑完变异再回头数）。
   三套固定皮（paper 2 / graphite 5 / zinc 0）用它和真值表交叉校验 —— 三个数**精确复现**，
   说明这个算法本身可信，种子才用它自己的值。

## 16. 线条收敛：少画线，而不是把线调淡（R16）

用户反馈"线条太明确了，太显眼了"。先量，再动手。

### 16.1 量出来的东西

写了个探针把页面上**每一条可见描边**按"它与相邻底的对比度"排序（线抢不抢戏，
看的不是有没有，而是对比度 —— 1px 的线一旦压到 3:1 以上，眼睛就把它当**图形边界**看，
而不是当分隔看）。zinc 下的结果：

| 指标 | 值 |
| --- | --- |
| 有描边属性的边 | 210 条（宽度都还在） |
| **实际画出来的线** | **162 条**，其中 `--border`（#7d7d86）画的约 180/162 中的绝大多数，对比度 **3.98–4.08:1** |
| `--border-strong`（#27272a）画的 | 14.5–15:1（近乎纯黑细线） |
| 最吵的单项 | `span.ft-chip` **28 条**（文件树里一列 PNG/JSON/MD 小方框） |

也就是说：**不是线多，是每一条线都太重**。zinc 的 `--border` 压白底 4:1，
比 WCAG 1.4.11 给非文字图形定的 3:1 门槛还高一档 —— 每一处分隔都在喊"这里有东西"。

### 16.2 为什么不是把线调淡

`skins.css` 的 zinc 块里已经写着这件事：

> 描边 ≥3:1 是 AA 的下限：#7d7d86 是「还能叫浅灰细线」的最深解，再淡一档
> （Tailwind 的 #e5e5ea）只剩 1.26:1 —— 好看但不满足 1.4.11……
> 要更 airy 的话**唯一正确的做法是少画线**（用留白/底色差分识别组件），不是把线调淡。

所以本轮做的是**减少线的条数**，不是降低线的对比度。

### 16.3 做法：一个按皮肤分档的"装饰框"令牌

新增三个令牌，把"这一条线要不要画"变成**皮肤的属性**：

| 令牌 | brutal 档（paper / graphite） | 产品风档（zinc / seed） |
| --- | --- | --- |
| `--edge-ink-soft` | `var(--border)`（硬边照旧） | `transparent` |
| `--edge-ink-soft-off` | `var(--text-faint)` | `transparent` |
| `--chip-edge` | 不定义 → 回落到类型色 | `transparent` |
| `--shadow-control` | `var(--sh-hard-sm)` | `none` |

**边宽照旧**（1px/2px 都留着占位），只换**颜色** —— 所以关掉框不会让布局宽度跳一下。

改了 **25 个规则块**：文件类型 chip、顶栏按钮/图标按钮/分区入口、树区域行、
对话台按钮与 chip、建议问句 pill、发送按钮、代码面板 badge、对话框按钮。

**保留的是结构线**：顶栏底线、侧栏右边、树头底线、输入框边界、弹层外框、菜单外框、
虚线空态框 —— 那些线在**划分区**，删了就没有结构了。判定标准是"这条线在区分什么"，
不是"这条线好不好看"。

### 16.4 两个连带发现

1. **无框控件不投影**。图标按钮这类既没底色也没框的元素，硬投影等于画出一个看不见的
   矩形，纸底上读起来还是一条明确的线（种子的树头部那三个按钮就是这个样子）。
   所以加了 `--shadow-control` 档，产品风档取 `none`。
2. **关框后 hover 必须还在**。写了个探针逐个悬停关键控件，量底色/字色/边框/位移有没有变：
   第一轮 7 个里有 1 个（分区入口的关闭态）**完全没反应** —— 它原本的 hover 底色
   和常态底色都是 `--bg-raised`，等于一直没反馈。补成 `--bg-hover` 后 7/7 全过。
   这是"少画线"最容易踩的坑：框一去掉，控件看着就像不能点。

### 16.5 结果

- **实际画出来的线：162 → 34 条**（zinc，-79%），剩下的 34 条全是结构线。
  种子皮肤同步到 34 条；**paper / graphite 仍是 158 条，一根没少**（brutalist 身份）。
- 视觉回归：**paper / graphite / 问答页 0 像素变化**（brutalist 身份分毫未动），
  只有 zinc 变化 7748 像素（0.6%），标红图确认**全部是"框被去掉"**，没有一处错位。
- 门禁：typecheck/build ✅ ｜ eslint 16 条（既有）｜ 令牌对 31 ✅ ｜ 皮肤状态 48 无退步 ✅
  ｜ 视觉回归 5/5 幂等 ✅ ｜ 画布 3:1 探针 9 项无退步 ✅

### 16.6 想更 airy 还能往哪走

本轮只动了**装饰框**，结构线的对比度没碰（它们仍在 3:1 以上，守着 AA 下限）。
如果还嫌重，下一步的候选是：

- 结构线本身降到 1.2–1.5:1（要放弃 1.4.11 的 3:1 判据）；
- 树区域行那种"框 + 彩色图标"改成"缩进 + 彩色图标"，一个框都不画；
- 弹层/菜单外框改成阴影表达（但那正是 brutal 档的签名，要分档做）。

## 17. 边框分档：把 1.4.11 用对地方（R17）

第 16 轮把"线太多"解决了（162 → 34 条），用户反馈"**还是重**"。
这轮不再猜，去看主流产品的实际取值。

### 17.1 三家产品的实测值

| 产品 | 角色 | 值 | 对比度 |
| --- | --- | --- | --- |
| GitHub Primer（亮） | `border.default` 组件外框 | `#d0d7de` @ `#ffffff` | **1.45:1** |
| GitHub Primer（亮） | `border.muted` 分隔线 | `#d8dee4` @ `#ffffff` | **1.36:1** |
| GitHub Primer（亮） | `border.subtle` | `#eaeef2` @ `#ffffff` | **1.17:1** |
| GitHub Primer（暗） | `border.default` | `#30363d` @ `#0d1117` | **1.55:1** |
| GitHub Primer | `shadow-resting` | `0 1px 0 rgba(31,35,40,.04)` | **4% alpha** |
| Linear（暗） | 默认 1px 分隔线 | `rgba(255,255,255,.05)` | **1.15:1** |
| Linear（暗） | 卡片外框 | `rgba(255,255,255,.08)` | **1.26:1** |
| Linear（暗） | 最外层实心框 | `#23252a` @ `#08090a` | **1.36:1** |
| Tailwind | `gray-200` | `#e5e7eb` @ `#ffffff` | **1.24:1** |

**关键发现**：连这些产品**最强**的边框都只有 1.36:1。Linear 的描述写得很直白 ——
"edges read as light-catching rather than hard lines"。而 GitHub 的 resting shadow
只有 **4% alpha** —— 深度来自 1px 发丝线 + 极小的底色差，不是来自"把线画深"。

### 17.2 之前那条规矩用错了地方

`skins.css` 的 zinc 块里原本写着：

> 描边 ≥3:1 是 AA 的下限……要更 airy 的话**唯一正确的做法是少画线**，不是把线调淡。

前半句**把 1.4.11 用错了地方**。WCAG 1.4.11 原文：

> It mandates a minimum contrast ratio of 3:1 between the visual presentation of
> the following two categories … **User Interface (UI) Components**: The visual
> boundaries or indicators that identify interactive controls such as text inputs,
> checkboxes, radio buttons, toggle switches, dropdown menus, and buttons.
> … **Essential or decorative graphics**: Graphical objects where the particular
> presentation is essential … or that are **purely decorative are exempt**.

也就是说 3:1 管的是**控件边界**与**承载信息的图形**；卡片外框、列表分隔线这类
纯装饰的图形对象**明确豁免**。Primer 自己的可访问性说明也是同一句：
"3:1 for UI elements and graphics — **No contrast requirement for decorative
and disabled elements**"。

之前把"所有描边都要 ≥3:1"当成不可退让的审美下限，等于把**装饰性**的边框也算进了
1.4.11 —— 于是 316 处引用全部压到 4:1 / 15:1，每条分隔线都在喊"这里有东西"。

### 17.3 改成三档

| 档 | 角色 | zinc 取值 | 对比度 | 1.4.11 |
| --- | --- | --- | --- | --- |
| `--border` | 容器外框 / 分隔线 | `#dcdce3` | 1.37:1 | 豁免（装饰） |
| `--border-strong` | 强调分隔 / 浮层框 | `#b9b9c4` | 1.95:1 | 豁免（装饰） |
| `--border-graphic` | 控件边界 + 承载信息的图形 | `#7d7d86` | 4.08:1 | **管** |

- **19 处控件边界**提到 `--border-graphic` 档（输入框、复选框、下拉、搜索框、代码框）。
  清单是**从模板里提取真正用在 `<input>/<textarea>/<select>` 上的 class** 再回查 CSS 得到的，
  不是靠正则猜的 —— 20 个文件里 300 多处 `--border` 引用，靠静态扫不准。
- **流程图的连线**也提到这一档：它是承载信息的图形（1.4.11 管 "graphical objects"），
  而且 `style.css` 里那条规则的注释本身就写着「连线 paper 2.01:1、zinc 2.13:1，几乎看不见」——
  早先用 `var(--border)` 修过一次，`--border` 变淡之后问题复发。
- 令牌改名 `--border-control` → **`--border-graphic`**：这一档同时服务控件边界和
  承载信息的图形，叫 "control" 用在连线上读着不对。

paper / graphite（brutalist 档）**保持硬边不变** —— 黑色/白色实心边是它们的设计身份，
不是"画重了"。四套皮肤实测：

| 皮肤 | `--border` | `--border-strong` | `--border-graphic` |
| --- | --- | --- | --- |
| paper | 墨边 15:1 | 墨边 15:1 | 墨边 17.7:1 |
| graphite | 白边 12:1 | 白边 12:1 | 白边 12.2:1 |
| zinc | `#dcdce3` 1.37 | `#b9b9c4` 1.95 | `#7d7d86` 4.08 |
| seed（生成） | `#dcd6d6` 1.35 | `#bcb1b0` 2.04 | `#9a8a89` 3.21 |

### 17.4 生成器要解算"落在某一档"，不是"至少某一档"

`ensure_contrast` 只保证"至少 target"—— 种子皮肤的 `--border` 按 1.6 目标解算，
实际落在 **2.73:1**，比主流产品重一整档。新增 `tune_contrast()`：扫明度区间，
取**达标且对比度最小**的那一档（对比度随明度单调，所以浅底上停在"刚好达标的最亮一档"、
深底上停在"最暗一档"，两个方向不用分别处理）。种子三档现在落在 1.35 / 2.04 / 3.21。

### 17.5 门禁也跟着改

- `verify_canvas_contrast.mjs`：HTML 侧的描边测量从"所有 ≥1.5px 的边框"收窄到
  **表单控件**（1.4.11 管的正是这一类），容器边框不再被当判据。
  门槛同时从 1.5px 放宽到 0.5px —— 收窄的是**对象**不是**精度**。
  改完立刻抓出三个真缺陷：流程图的筛选框、HarnessPanel 的 input/select，
  边框都挂在容器档上（paper 1.38:1 / zinc 1.36:1），已提档。
- `verify_skin_token_pairs.mjs`：新增 4 项「`--border-graphic` 对 `--bg-raised` ≥ 3:1」
  —— 把 1.4.11 守在**它真正管的地方**，而不是守在每一条装饰线上。35 项全过。

### 17.6 结果

- 视觉回归：**paper / graphite / 问答页(paper) 0 像素变化**（brutalist 身份分毫未动）；
  zinc 与 ask-zinc 按预期变（12968 / 12623 px ≈ 1%），标红图确认全是"线变淡"。
- 门禁：build ✅ ｜ eslint 16 条（既有）｜ 令牌对 **35 项全过**（含 4 项新判据）｜
  皮肤状态 **48 状态无退步** ｜ 视觉回归 **5/5 幂等** ｜ 画布 3:1 探针 **9 项无退步** ｜
  hover 反馈 **7/7 控件全过**。

## 18. 线宽与「不必要的线」（R18）

用户看了 R16/R17 的结果仍然说"**还是重，线条太粗了，有些地方根本没必要用线条**"。
这轮把"线"拆成三个独立维度来治：**多粗**、**多密**、**多亮**。

### 18.1 线宽：统一 1px

原来分三档（`--edge-w` 1px / `--edge-w-strong` 2px / `--edge-w-heavy` 3px），
全仓约 60 处用 strong/heavy。问题在于**"2px 细线"已经不是线了 —— 它是一道描边**。
在深色皮肤上尤其扎眼：graphite 的 2px 白边在 #16181d 上是 12:1 的发光带。

现在所有皮肤统一 1px（种子的 `border_w` 候选也收到 `[1,1,1,1]`，
RNG 调用次数不变，所以种子的其它派生参数保持可复现）。
brutalist 档的身份改由**别的东西**承担：零圆角 + 硬偏移阴影 + 墨白配色。

### 18.2 密度：装饰框在所有皮肤都关掉

R16 引入的 `--edge-ink-soft`（装饰框档）当时只给 zinc 设了 `transparent`，
paper / graphite 仍是 `var(--border)` —— 因为当时把"硬边"当成了那两套皮肤的身份。
现在改成**所有皮肤都关**：框在 chip / 次要按钮 / 图标按钮 / 树区域行上从来不承载信息，
区分靠底色、字色、缩进和图标。

`--chip-edge`（文件类型 chip 的**类型色**边框）同样全局关掉 —— chip 已经有同色系底纹 + 文字，
再套一圈彩框是第三遍表达同一件事。

关掉之后，四套皮肤的**实际画出来的线**都是 34 条（原先 162 条），
剩下的全是结构线：顶栏底线、侧栏右边、树头底线、输入框边界、搜索框边界、
弹层/菜单外框、选中态描边、流程图连线。

### 18.3 亮度：深色皮肤的线用暗白，不用纯白

graphite 剩下那 34 条线全是 **12–14:1 的纯白** —— 在深底上每一条都在发亮。
这跟浅色皮肤是反的：浅底上的深线读起来像**印刷**（墨在纸上），深底上的亮线
读起来像**电路图**。Linear 在深底上用的是 5%~8% 的白，Primer 深色的
`border.default #30363d @ #0d1117` 是 1.55:1。

于是 graphite 换成暗白三档（`--ink` 仍是亮白，那是文字色）：

| 档 | 值 | 对比度 | 参照 |
| --- | --- | --- | --- |
| `--border` | `rgba(255,255,255,.13)` | 1.51:1 | Primer 深色 border.default 1.55 |
| `--border-strong` | `rgba(255,255,255,.26)` | 2.35:1 | — |
| `--border-graphic` | `rgba(255,255,255,.45)` | 4.2:1 | 1.4.11 管的 ≥3:1 |

paper 保持墨边：浅底上的深线是印刷感，天然合适。

### 18.4 又去掉一处：空态按钮的框

`.ov-empty-btn`（"去启用分区治理"）同时有强调色底纹、强调色字和一圈强调色边框 ——
第三遍表达同一件事。框去掉，宽度留着（transparent）以免布局宽度跳一下。

### 18.5 结果

- 可见线：162 → **30 条**（四套皮肤同数），其中剩下的全是结构线：
  控件边界 3.98–4.49:1（1.4.11 管的那一档）+ 结构分隔 1.36–2.35:1。
- 门禁：build ✅ ｜ eslint 16 条（既有）｜ 令牌对 **35 项全过** ｜ 视觉回归 **5/5 幂等** ｜
  画布 3:1 探针 **9 项无退步** ｜ hover **7/7（zinc + graphite）**。

## 19. 一道补上的门禁：产物必须比源码新（R19）

R18 交付后用户回："**这不是一样吗**"，并贴了一张截图 —— 截图里 chip 还有彩框、线还是亮的。

查下来是：**`web/` 里的构建产物比源码旧**。R18 的改动在源码里、在我的构建日志里（`✓ built`），
但**没进到 `web/`** —— 原因是这个仓库有并发写者，大家共用同一个 vite 输出目录
（`outDir: ../web`，且 `emptyOutDir: false`），**谁后跑谁覆盖**。

危险的地方在于：所有门禁都是"对着服务出来的页面量"的，量到的也是旧产物，
于是**所有指标全绿**，没人发现"改动根本没生效"。我甚至在交付前用截图验证过 ——
验证的对象本身就是旧的。

新增 `verify_product_fresh.mjs`：比对 `frontend/src` 里最新的源文件与
`web/{index.html,workbench.html,assets/}` 里最旧的产物文件，前者更新就报红。

```
最新源文件：frontend\src\workbench\skins.css  2026/10/20 16:09:00
最旧产物文件：web\assets\space-grotesk-...woff2  2026/10/20 16:10:29
PASS 产物不旧于源码
```

两个实现细节：
- 只比 **vite 产出的那部分**（`index.html` / `workbench.html` / `assets/`）——
  `web/` 里还有 `favicon.ico`、`trace.html`、`session.js` 这些 vite 不管的文件
  （`emptyOutDir: false` 就是为了保住它们），拿它们比新鲜度会永远报旧。
- 判据用**修改时间**而不是内容比对：内容比对要先知道"应该有什么"（要维护一份指纹），
  修改时间零成本，且"产物比源码旧"这个事实本身就是病根。

顺带把上一轮那张"其实一样"的截图也解释清楚了：它就是 R18 之前的产物。

## 20. 深底上的线要再暗一档（R20）

R19 交付后用户又回："**这不是还有很明显的白线吗**"，并贴了真实应用的截图。

量出来的问题不是"还有框"，而是**档位本身在深底上就偏亮**：

| 档 | R19 定的值 | 深底上的观感 |
| --- | --- | --- |
| 分隔线 | 13% 白 = 1.51:1 | 顶栏底线、侧栏边、树头底线三条长线仍然一眼可见 |
| 控件边界 | 45% 白 = 4.2:1 | 输入框是屏幕上最亮的东西 |

### 20.1 关键洞见：同一个对比度，浅底和深底不是一回事

**1.4:1 的线在白底上只是隐约一条，在深底上却刺眼** —— 亮-暗对比被眼睛放大，
深色 UI 里"少量提亮"的感知强度远高于浅色 UI 里"少量压暗"。

所以深底皮肤的档位必须比浅底**再低一档**。参照值（都是实测）：

| | 浅底 | 深底 |
| --- | --- | --- |
| 分隔线 | Primer `border.muted` 1.36 · Tailwind gray-200 1.24 | Linear 5% 白 **1.15** · Primer `border.muted` **1.28** |
| 组件外框 | Primer `border.default` 1.45 | Primer `border.default` **1.55** |
| 控件边界 | 1.4.11 ≥ 3.0 | 1.4.11 ≥ 3.0 |

（Linear 的原话："Keep card borders at 1px with low-opacity white (≈8% opacity) so
edges read as light-catching rather than hard lines."）

### 20.2 改成什么

| 皮肤 | 分隔线 | 组件外框 | 控件边界 |
| --- | --- | --- | --- |
| zinc（浅） | `#dcdce3` 1.37 | `#c9c9d2` 1.64 | `#8f8f95` 3.14 |
| graphite（深） | `rgba(255,255,255,.07)` **1.24** | `rgba(255,255,255,.13)` **1.51** | `rgba(255,255,255,.38)` **3.57** |

两处**不能再低**：
- 分隔线已经到 1.15–1.25（Linear / Primer 深底的量级），再低就不是线了。
- 控件边界（输入框、搜索框）是 1.4.11 明确管的"哪里能点"，
  实测 28% 白只有 2.52:1，低于底线，所以停在 38%（3.57:1）。
  **这一档是"看起来还是有点亮"与"看得见能点"之间唯一站得住的位置。**

深色皮肤上卡片与背景的区分改由**表面色差**承担（`--bg #16181d` → `--bg-raised #22262e`），
这正是 Linear 的做法（surfaces 阶梯 + 发丝线），而不是靠一条更亮的框。

## 21. 玻璃模式下「更多」点了没反应（R21）

用户报：**切到玻璃材质后点「更多」没反应**。

### 21.1 症状

菜单其实**开了**（`moreMenuOpen` 为真、坐标也对），但画面上只在上方多出一道很淡的边，
菜单项一个都看不见；而且点击落点命中的是 `nav.ws-bar`（工作区栏）而不是菜单。

### 21.2 根因：`backdrop-filter` 让顶栏成了 fixed 定位的包含块

`.wb-menu` 是 `position: fixed`，本意是"逃开顶栏的 `overflow-y: hidden` 裁剪"
（`style.css:887` 的注释早就写过这个失败模式：*"绝对定位的菜单向下伸出顶栏会被裁掉
（不可见且不命中点击，只剩透明遮罩吃点击 = 菜单"没反应"）"*）。

当年靠把菜单改成 `fixed` 修好了 —— 但 **`position: fixed` 只有在祖先不建立包含块时**
才逃得出 `overflow` 裁剪，而**玻璃模式的顶栏带 `backdrop-filter`，它恰恰就是那个包含块**。
于是：

- 菜单被顶栏的 `overflow-y: hidden` 裁到只剩顶边一条（用户看到的那道淡影）；
- `.wb-menu-backdrop`（`inset: 0`）同样被裁成只剩顶栏高度 → **那层透明遮罩还在吃点击**；
- 菜单项在裁剪区外 → 命中测试打到下面的 `nav.ws-bar`。

实测：solid 模式命中 `div.wb-menu-label`（在菜单内）✅；glass 模式命中 `nav.ws-bar` ❌。

### 21.3 修法：Teleport 到 body

`style.css:871` 的注释本来就写着「面板弹层**仍 teleport 到 body**」——
设计意图就是 teleport，只是标记里没做。补上：菜单与遮罩一起 `<Teleport to="body">`。

Teleport 之后菜单既不在顶栏的裁剪范围内，也不再受任何祖先 `backdrop-filter` 影响，
两种材质行为完全一致：

| | solid | glass |
| --- | --- | --- |
| 菜单完整可见 | ✅ 573px | ✅ 575px |
| 遮罩覆盖视口 | ✅ 900px | ✅ 900px |
| 菜单项可见 / 可命中 | 10 / 10 | 10 / 10 |
| 点菜单项有反应 | ✅ 代码地图面板打开 | ✅ 代码地图面板打开 |

顺带把 `.wb-menu-item` 排除出玻璃的通用按钮规则（⑤）：它是**菜单行**不是按钮，
套上玻璃规则后每行都变成独立白卡（一摞卡片），而菜单本体已经是一块面板，
两种材质下菜单会长得不一样。现在两种材质都是"一块面板里的普通行"。

### 21.4 顺带挖出的另外两处

**项目切换菜单**（`.wb-proj-menu`）是同一类结构 —— 顶栏里的 `position: fixed`，
玻璃模式下被同一个机制裁掉。实测：solid 遮罩 900px / 命中在菜单内 ✅；
glass 遮罩只剩 **51px** / 命中 `header.ft-head` ❌。一并 teleport 到 body。

**顶栏搜索面板**（`.lb-pop`）更糟：它是 `position: absolute` 挂在顶栏里，
而顶栏有 `overflow-y: hidden`（窄宽兜底要横向滚动）→ **两种材质下都被裁**，
而且宽度按错的包含块算（实测 841px，搜索框只有 220px）。这个与玻璃无关，
是长期存在的坏功能（面板完全看不见，只有一层透明遮罩在吃点击）。
改成 teleport 到 body + `fixed`，坐标与宽度按**可见的输入框**（`.lb-box`）算 ——
注意不能按根节点算：根节点被 `.wb-locate-slot` 的 `flex: 1 1 auto` 撑成整条顶栏那么宽。

teleport 之后 `onDocClick`（"点在面板外就关闭"）会把"点面板里的结果"当成点外面，
面板当场消失 —— 所以那处判定要同时看根节点**和**面板 ref。

## 22. 玻璃模式下的"隐形按钮"（22）

用户：**里面的素材按钮好像点开也没用**。

### 22.1 症状

素材中心（`/workbench` → 素材）左上角的类别胶囊和搜索按钮，在玻璃材质下**只剩一个空框**：
按钮有形状、有位置，但**看不见字**。问答页侧栏的「新对话」「上传」两个按钮同样如此。

### 22.2 根因：不是按钮坏了，是玻璃规则盖掉了填色

先排除"功能坏了"：实心材质下同样的按钮点击行为完全正常（切类别能切、搜索能搜、卡片能开抽屉）。
所以问题出在**视觉**：按钮的底被换掉了。

`glass.css` ⑤ 给**所有** button 发半透白底：

```css
html[data-material='glass'] :is(button, .wb-btn, .dg-primary, .cd-send, .acp-compose > button):not(:disabled):not(.wb-menu-item) {
  background: color-mix(in srgb, var(--bg-raised) calc(var(--glass-d2-alpha) * 100%), transparent);
}
```

而「填色按钮」（底是强调色、字是 `--accent-ink` = 白）自己写的是：

```css
.ac-search-btn { background: var(--accent); color: var(--accent-ink); }
```

**关键在于特异性**：这条玻璃规则的实际特异性是 **(0,4,2)** ——

`html` (0,0,1) + `[data-material]` (0,1,0) + `:is(button, .wb-btn, …)` 取参数里最高的
`.acp-compose > button` (0,1,1) + 两个 `:not()` 各 (0,1,0) = 类/属性 **4** 个、元素 **2** 个。

而组件里 `.ac-search-btn[data-v-05957e08]` 只有 **(0,3,0)**。**玻璃规则赢**，
于是强调底被换成半透白，白字压半透白 = **1.01:1**（等于没有字）。

> 顺带更正一个容易踩的坑：`:is()` / `:not()` 各自取**参数里最高的那个**特异性，
> 所以 `html[...] :is(button, .x) :not(:disabled) :not(.y)` 不是"低特异性的大范围规则"，
> 它比绝大多数组件规则都高。想让组件赢，得靠 `!important` 或 `#id` 兜底 —— 但那是在跟级联硬碰硬。

### 22.3 修法：一个 `--btn-fill` 逃生口（而不是给每处加 !important）

CSS 无法在级联里区分"这个按钮有填色"和"这个按钮是中性底"。所以定一个约定：

> **组件自己声明 `--btn-fill` 表示"这个按钮的底是我的，玻璃不许动"**；
> 玻璃规则用 `var()` 的兜底值把半透白留给普通按钮。

`glass.css` ⑤：

```css
background: var(--btn-fill, color-mix(in srgb, var(--bg-raised) calc(var(--glass-d2-alpha) * 100%), transparent));
```

⑤'（顶栏那组按钮，强制不透明）同样让路：

```css
background: var(--btn-fill, var(--bg-raised)) !important;
```

然后在所有填色按钮上声明 `--btn-fill`（与 `background` 同一个值，hover 也一起声明，
否则玻璃模式下 hover 变深的反馈会丢）。共 **17 个组件 / 30 处**：

| 位置 | 声明 |
| --- | --- |
| 素材中心 `.ac-kind.on` / `.ac-search-btn` / `.ac-primary`(+hover) | `var(--accent)` / `var(--accent-deep)` |
| 素材生成 `.ag-primary` / `.ag-primary-cloud` | `var(--accent)` / `#8b6cf0` |
| 适配器 `.rollback-box button` | `var(--accent)` |
| 对话台 `.cd-switch.on` / `.cd-chip-native .cd-switch.on` | `var(--accent)` / `var(--tool)` |
| 舱面板 `.hp-btn.primary` | `var(--accent)` |
| 模型设置 `.ms-primary` | `var(--accent)` |
| 设置页 `.sv-primary` / `.sv-skin.on` / `.sv-layout.on` / `.sv-mat.on` | `var(--accent)` / `var(--accent-soft, var(--bg-hover))` |
| 任务引擎 `.te-action,.te-engine button` / `.te-comfy button` / `.te-cancel` / `.te-output button` / `.te-unreal button` | `var(--accent)` / `var(--danger)` |
| 门禁对话框 `.wg-primary`(+hover) | `var(--accent)` / `var(--accent-strong, var(--accent))` |
| 流程预览 `.vp-pop-foot button, .vp-image-feedback button` | `var(--accent)` |
| 选区 AI `.ai-send`(+hover) | `linear-gradient(…)` / `var(--accent)` |
| 语义定位 `.lb-tagbtn`(+hover) | `color-mix(…)` / `#e0ecfd` |
| 共享层 `.wb-save-btn`(+hover) / `.wb-revert-btn`(+hover) / `.dg-primary`(+hover) | `var(--accent)` / 琥珀渐变 |
| 问答页 `.btn` / `.tb-btn.primary` / `.send-btn` / `.chip.on` / `.suggestion:hover` / `.cap-chip:hover` / `.followup:hover` | `var(--accent)` |
| 问答页 `.ref-chip:hover` / `.ask-opt:hover` / `.ask-box.is-perm .ask-opt:hover` | `var(--accent)` / `var(--amber)` |

**反向也要能退出**：`.btn.ghost`（灰底）与 `.send-btn.stop`（中性底）继承同一个元素上的
`--btn-fill`，必须显式写 `--btn-fill: initial` 才能让它们回到"中性按钮"。

### 22.3.1 第二条约定：`--btn-ink`（填色底上该用什么字色）

只补 `--btn-fill` 还不够。玻璃 ⑤'（顶栏那组按钮）会强制 `color: var(--text) !important`，
而深色皮肤里 `--text` 是**浅色** —— 于是"强调色底 + 浅字"在 graphite 上只有 **1.47:1**。
所以再定一条：

> **`--btn-ink` = 这个填色底上的字该是什么色**（强调色底 → `--accent-ink`，琥珀底 → `--amber-deep`）。

玻璃规则改成 `color: var(--btn-ink, var(--text)) !important`，
只有真正填色的按钮才声明 `--btn-ink`，中性按钮继续走 `--text`。

### 22.3.2 顺带踩到的坑：令牌不能挂在**共享基类**上

`.wb-save-btn` 是顶栏的**共享基类**，"保存 / 问答页 / 设置 / 更多 / 历史 / 撤销"六个控件全挂着它。
我一开始把 `--btn-fill: var(--accent)` 写在基类上，结果：

- 玻璃模式下整排顶栏按钮都被刷成强调色（"设置""更多"本来是中性底）；
- graphite 皮肤下浅字压青底 = 1.47:1 —— **这是我自己引入的回归**，
  而且第一版探针只扫了 zinc，把它漏过去了（多皮肤扫描才抓到）。

修法是把 `--btn-fill` 从基类挪到一个**排除变体**的选择器上：

```css
.wb-save-btn:not(.wb-icon-btn):not(.wb-history-btn):not(.wb-revert-btn) {
  --btn-fill: var(--accent);
  --btn-ink: var(--accent-ink);
}
```

> 教训：**令牌要挂在"语义确定的元素"上，不要挂在"共享样式基类"上**。
> 基类上的声明会顺着 class 列表漏给所有变体 —— 而级联不会提醒你。

这套约定的好处是**实心材质零影响**：`--btn-fill` / `--btn-ink` 在实心模式下没有任何规则读它，
所以视觉回归 5/5 像素零变化。
