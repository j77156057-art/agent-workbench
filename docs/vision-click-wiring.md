# 视觉定位点击：把"看着画面找目标"接给模型

> 2026-10-21。承接 [agent-engine-browser-wiring.md](agent-engine-browser-wiring.md)。
> 本文记录第三条"把后端已有能力接给**模型**"的线：**视觉定位点击**。

---

## 1. 起点：模型能看图，却点不到画布上的东西

模型操控界面有两条路：

| | 定位方式 | 覆盖不到 |
| --- | --- | --- |
| `dev_page_action` | DOM 锚点（CSS 选择器 / 可见文字） | **canvas / 图表 / 位图按钮在 DOM 里是空的** |
| 视觉定位 | 让视觉模型看图给 bbox | 此前**只有 HTTP 端点，agent 够不着** |

后端其实早就有视觉定位点击（`POST /api/vision/locate-click` + `/api/vision/execute-click`），
但那条链只有 **HTTP 端点 + 前端**，**没有任何 agent 工具** —— 于是模型能看图、能截图，
却**不能看着画面找到要点的那个按钮**。

差别不是"少个按钮"，而是这类任务（游戏画面、图表、渲染型 UI）**整个做不了**：
模型能描述画面里有什么，但没法据此操作。

## 2. 这次补上的

### 2.1 一处实现，两个出口

核心搬到 `agent_runtime/visual_click.py`，HTTP 端点与两个 agent 工具共用：

| 出口 | 用途 | 「用户确认」来自 |
| --- | --- | --- |
| `POST /api/vision/locate-click` / `execute-click` | 前端点 | **前端 UI 点了确认**（`confirmed=true`） |
| `vision_locate_click` / `vision_click`（新 agent 工具） | 模型用 | **审批台账**：用户在工作台审核队列批准，agent 用**完全相同**的参数重试 |

共用的是同一份提案存储、同一套画面指纹复核、同一套复验判据。所以
「UI 定位的提案」与「模型定位的提案」是同一种东西，谁都能执行。

### 2.2 定位与执行**必须**分成两个工具

合成一个工具的话，模型会以为"定位成功 = 可以点"。拆开之后，
"点了没有"这件事由**执行**工具的返回值说话（`ok` / `effect` / `verification`），
而不是由定位的乐观结果暗示。

### 2.3 确认来自用户，不来自模型

agent 出口走**既有的审批通道**（`desktop_action`）：

1. 首次调用 → `require_approval` 拦下 → `record_gate_request` 把请求写进审核队列；
2. 用户在工作台的审核队列看到请求并批准 → 审批台账写入 approved 记录；
3. agent 用**完全相同的参数**重试 → `is_approved` 命中 → 真的点。

**模型自己说"我确认了"不算** —— 那等于自我授权。`dev_approve` 的 action 白名单里
也没有这一类，只能由用户在工作台确认。

审批 target 与 `dev_desktop_action` **同一套格式**（`desktop:click:embedded:<坐标哈希>`）：
两类点击在同一个审核面板批准，且**批准后换坐标必须重新批准**。

### 2.4 三道闸，缺一不可

1. **用户批准**（见上）；
2. **画面复核**：执行前重新抓帧，窗口句柄要一致、目标位置的像素指纹要一致。
   定位时看到的是这个按钮、点的时候已经不是了 —— 这时必须不点；
3. **提案单次使用**：标记必须在真正发点击**之前**，否则重复请求能连点两次。

### 2.5 视觉模型的三条来源

按顺序找，找到一个**能力画像确认为原生视觉**的就用：

1. **开发舱固定模型**（`/api/vision/*` 端点用的那个）；
2. **当前主模型**（若它本身就是原生视觉模型）；
3. **Harness 视觉模型**（`DOCMIND_VISION_MODEL` + 同前缀 provider/key/base_url）。

第 3 条是纯文本主模型时**唯一**能走通的路。

**能力画像没确认视觉的一律不用**（除非显式 `DOCMIND_VISION_ALLOW_UNVERIFIED`）——
拿一个只会读文本的模型去猜坐标，产出的是"看起来像"的位置，点下去就是点错地方。
错误文案把三条路都写出来，并明确"不要用只读文本的模型去猜坐标"。

## 3. 途中修掉的两处

### 3.1 两份提案存储

提案存储原本是 `api._VISUAL_CLICK_PROPOSALS`。搬到新模块时若在 api.py 留个**副本**，
就变成"两份提案存储"——UI 定位的提案会被模型说成"不存在"，模型定位的提案又没法在
UI 上确认，而**两边都"看起来正常"**。

改成**同一个对象的别名**（`_VISUAL_CLICK_PROPOSALS = visual_click.PROPOSALS`），
既有代码与测试照旧能用，且不可能分叉。

### 3.2 阻断结构没有 `ok` 键

`require_approval` 返回的阻断结构里没有 `ok`，而 `execute()` 的其它失败分支都带
`ok:false`。契约不统一的话，调用方（agent 工具、HTTP 端点）就得为这一种失败单独写判断。
补上 `ok:false`。

## 4. 验证

### 4.1 新增护栏测试（15 项，`tests/test_visual_click.py`）

离线（不真跑视觉模型、不真点屏幕），测的是"该被拦的**一定**被拦"：

| 场景 | 期望 |
| --- | --- |
| 没有视觉模型 | 明确报错并说清去哪儿配 |
| `description` 为空 | 400 |
| 没有嵌入窗口 | 明确报错 |
| 模型答案不可信（把握度低 / 无依据 / 坐标非法 / 不是 JSON） | **不产出提案** |
| 定位成功 | 产出含坐标、指纹、标签、证据的提案 |
| 没有提案 | 404 |
| **没有任何确认** | **不点**（模型的自称确认不算） |
| 走审批门但未批准 | 阻断 + `approval_required` + 指引去审核队列；**不点** |
| 批准之后 | 真点**一次**；同一提案再调 → 409 |
| 目标像素变了 | 409，**不点** |
| 窗口换了 | 409，**不点** |
| 别的项目执行提案 | 404（不泄露它是否存在） |
| 审批 target 稳定性 | 同坐标→同 target；换坐标→换 target；格式与 `dev_desktop_action` 一致 |

### 4.2 既有测试未破

`tests/test_visual_targeting.py`（11 项，测 HTTP 端点）**全过** —— 端点重构后行为不变。

### 4.3 真实环境下的失败路径（不打桩）

| 调用 | 实际返回 |
| --- | --- |
| `vision_locate_click`（本机无桌面宿主窗口） | `{"ok": false, "status": 400, "error": "当前项目没有已登记的嵌入窗口，无法定位目标。请先启动并嵌入项目窗口，或用 game_screenshot 之类的观察工具。"}` |
| `vision_click`（无项目上下文） | `{"ok": false, "error": "未配置当前项目。"}` |
| `resolve_vision_llm`（本机未配视觉模型） | 明说三条路 + "不要用只读文本的模型去猜坐标" |

### 4.4 ⚠️ 真机路径**未验**

视觉定位点击的真机验证需要两样东西，本机都没有：

1. **桌面宿主窗口**（Agent 工作台 以 pywebview 嵌入窗口运行时才有可抓的嵌入窗口；
   本机跑的是 web 模式）；
2. **可用的视觉模型**（本机 `.env` 是 `qwen-plus`（文本），未配 `DOCMIND_VISION_MODEL`）。

所以"真跑一次视觉模型找到目标并点下去"这条路径**尚未实测**。已经实测的是：
护栏逻辑（15 项打桩测试）、既有端点行为未变、真实环境下的失败路径与提示文案。
配好上面两样之后，应当补一次端到端实测。

## 6. 还没做的

- **真机端到端实测**（见 4.4）：需要桌面宿主 + 视觉模型。
- **浏览器页面的视觉定位**：当前视觉定位只作用于**桌面嵌入窗口**。浏览器里的页面走
  `dev_page_action` 的 DOM 锚点更准，视觉定位对它是补充而不是替代 —— 两者共用同一份
  提案与复核机制，但抓帧来源不同（嵌入窗口 vs 浏览器页）。
