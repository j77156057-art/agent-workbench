# 调研纪律：什么算「已核实」

> 这份规范来自一次实际的调研失误。
> 起因是我把一份委派给 subagent 的提示词当成了「这次任务的说明」，
> 而它其实是一份**可复用的纪律范式** —— 现在固化成文。

## 为什么要有这份东西

`harness-research-verified.md` 记的是**结论**（三家的授权、供应链、限额…）。
但结论本身不保证可信 —— 结论的可信度取决于**它是怎么来的**。

这份文档管后者。**任何要写进 `harness-research-verified.md` 的结论，
先按这里自查一遍。**

---

## 一、十条硬规矩

### 1. 每条结论必须紧跟出处

格式：`文件路径:行号`，或官方文档 URL。

```
✅ opencode 把上下文类工具聚合成一组 — message-part.tsx:607
❌ opencode 会聚合工具调用（大概是这样）
```

**行号不是装饰。** 写不出行号 = 你没读到那段代码 = 结论不成立。

### 2. 找不到就写「未找到一手证据」，禁止推测

「未找到」是**合法结论**，「大概有」不是。

沉默的遗漏最危险：读者会以为「没提到 = 不存在」。
所以**必须显式列出没找到的项**（见第 8 条）。

### 3. 二手来源不得当事实

博客、聚合文章、他人转述 —— 只能用来**找到一手来源的线索**，
引用时必须标注为二手。**结论本身必须落在一手来源上。**

### 4. ⚠ **字面为真 ≠ 功能性结论**（本轮最大的教训）

**这一条是血的教训，而且不是从二手来源来的 —— 是从我自己核实的结论来的。**

上一轮 subagent 核实 opencode，结论原文：

> 「未找到 opencode 有独立『模型生成的过程叙述』事件类型」

这句话**字面为真**，我亲自核过：opencode 的 `SessionStatusEvent` 确实只有
`idle` / `busy` / `retry` 三态，没有 narration 事件。

**但我据此推出了「所以 opencode 只靠固定短语」—— 这个推论我从未核实。**

用户当场纠正：*「opencode 绝对不只是简单的固定短语，我正在用，每次调用工具都会补充一段话，
中途发现自己没做对还会老实承认错误然后修改计划重新调用。」*

**一个正确的核实结论，被我用一条未验证的推理链过度外推了。**

| 层次 | 例子 | 可靠性 |
|---|---|---|
| 事实 | `SessionStatusEvent` 只有三态 | 核实过 |
| **推论** | 「所以它没有轮中叙述」 | ❌ **推论不是事实** |
| 事实 | 模型在带 tool_call 的回合里写的 text part，UI 怎么渲染 | **要去查这个** |

**规矩：核实事件「不存在」，只能得出「没有这个**类型**」，
不能得出「没有这个**行为**」。** 行为可能由完全不同的机制产生 ——
普通 text part 交错渲染就够了，不需要专用事件类型。

### 5. 区分「内容」与「状态指示」

服务端状态机（`idle`/`busy`/`retry`）**不是**用户看到的聊天内容。
这两件事在同一段调研里经常同时出现，混为一谈就会得出错误结论。

规矩：描述 UI 时明确说**哪一层**（服务端事件 / 客户端组件 / 渲染分支）。

### 6. 仓库身份先核实，再核实内容

改名 / 重定向 / 镜像会让人核到不同的东西。

本轮实测（GitHub API）：

| 我给的 | 实际 | 怎么发现的 |
|---|---|---|
| `parallel-web/pi` | **404** | API 返回 Not Found |
| `badlogic/pi-mono` | **302 → `earendil-works/pi`** | 返回 `full_name` 不同 |
| `sst/opencode` | **重定向 → `anomalyco/opencode`** | 返回 `full_name: "anomalyco/opencode"` |

规矩：**先确认 `full_name` 与默认分支**，写进结论头部。

### 7. 网络受限时，明写替代读法

本轮环境阻断 `raw.githubusercontent.com` 与本机 `git`。

替代路径（可复现）：

```
GET https://api.github.com/repos/{owner}/{repo}/contents/{path}?ref={branch}
  -> JSON: content(base64) + encoding:"base64"  -> 解码
目录：同上，path 传目录名
搜索：https://api.github.com/search/code?q=...+repo:{owner}/{repo}
```

规矩：**把受限与替代读法写进结论**，否则下一个人会以为你读的是原始文件。

### 8. 必须有一节「未找到一手证据」

把没查到的显式列出来：

```
### 未找到一手证据的项
- Pi：无「模型生成的过程叙述」事件类型
- opencode：服务端无叙述层
```

规矩：这一节**不能为空**。若真的一项都没有，说明**没查够**。

### 9. 事实与设计建议分开写

「opencode 用 `ToolStatusTitle` 做动词切换」是事实。
「所以我们也该这么做」是建议。

**混在一起写，读者会以为建议也有出处。** 规矩：建议单独成节，
并标明「这是建议，不是核实结果」。

### 10. 结论要能被反驳

写完自问一句：**什么证据能推翻这条结论？** 想不出来，说明它太模糊。

## 二、委派提示词模板

⚠ **模板里的 `[方括号]` 是要替换的占位符。**
⚠ **下面第 1 行那段「你是被另一个会话委派的 subagent」是真实的会话前缀 ——
照抄会让 subagent 以为自己在跟上游会话说话。**

```
You are a subagent spawned by another session.
任务：[一句话写清要核实的**行为**，不要写「有什么功能」]

注意：[网络受限情况 + 可用的替代读源码路径 + 完整 URL 形式]

需要回答的核心问题：[用**行为**措辞，不要用「事件类型」这类实现措辞]

逐项核实并给**文件路径 + 行号**：

A. [最关键的那一项]
B. [...]
C. [...]

D. 上一轮的结论「[原话照抄]」是否需要修正？
   - 如果 A 成立，请明确说明修正后的措辞。
   - 请给出支撑这一措辞的代码位置。

E. [同类对象是否有同样机制？]

输出要求：
- 每条结论**必须紧跟出处**（`文件路径:行号`）。找不到就写「未找到一手证据」，**不要推测**。
- 最后单列一节「未找到一手证据的项」——这一节不能为空。
- 最后单列「对 [本项目] 的直接含义」，并标明哪些是事实、哪些是建议。
- 注意：[容易被混为一谈的两件事，明确要求区分]
```

### 关键：措辞要用「行为」而不是「实现」

| ❌ 会导致误判的措辞 | ✅ 不会误判的措辞 |
|---|---|
| 「有没有 narration 事件类型？」 | 「用户看到的『边干边说话』是怎么实现的？」 |
| 「有没有 interim 概念？」 | 「有没有把轮中散文与最终答案区分开的机制？」 |

**原因见第 4 条**：问「事件类型」会诱导出「没有这个类型」，
而这**掩盖了**「这个行为由别的机制实现」的可能。

## 三、这份规范自己的失误记录

规矩不是一次写对的。第一次起草时我把「未找到一手证据」写成了一条**可选项**，
理由是「有些调研确实全都找到了」。写完立刻发现：**如果全都找到了，
说明第 2 条（禁止推测）被违反过** —— 因为真实调研几乎总有查不到的项。

所以第 2 条和第 8 条必须绑死：**第 8 条为空 = 第 2 条被违反**。
