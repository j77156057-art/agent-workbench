# DocMind 设计系统 · 商业化验收标准 v1.0

> 本文档是**验收标准**，不是风格建议。每一条要么能被 `tools/design_acceptance.py` 自动判定，
> 要么明确标为人工评审项并给出判据。没有判据的条目不准写进来。

---

## 0. 这份标准解决什么

「做得更花」不等于商业化。商业化 UI/UX 的实质是**三件事**：

| 维度 | 用户感知 | 失效表现 |
|---|---|---|
| **可信** | 「这东西有人维护、敢付钱」 | 白线压白底、死令牌、按钮边界看不见 |
| **可扫读** | 「我三秒知道该点哪」 | 字号乱、间距不齐、一屏三个主角 |
| **可控** | 「我按错也能退回来」 | 无 focus 环、无禁用态、动效拖沓 |

对应到工程上，就是 10 条可判定规则 + 4 档成熟度。**目标是让「够不够商业化」不再靠感觉投票。**

---

## 1. 成熟度分档

商业化不是布尔值。同一套代码在四个档位上要求不同，**验收时先声明目标档位**，再逐条比对。

| 档位 | 名称 | 硬性要求 | 适用场景 |
|---|---|---|---|
| **L0** | 可运行 | 能跑、无白屏 | 内部 Demo |
| **L1** | 可内测 | L0 + R02/R05/R07/R08 全绿 + R10 三态齐 | 给种子用户试用 |
| **L2** | 可商用 | L1 + R01/R03/R04 **零新增** + 人工项 A 全过 | 对外收费 / 上架 |
| **L3** | 可规模化 | L2 + 全皮肤×全布局组合视觉抽检零破相 + 对比度逐组合实测达标 | 多租户 / 白标交付 |

当前仓库实测：**L3（可规模化）** —— 自动门禁 11/11 绿；人工项 A1–A6 全部通过；
组合矩阵 **60 组全通过、0 破相**（4 皮肤 × 5 布局 × 2 材质 + 工作台 2 调色板 × 5 × 2）。

## 2. 自动门禁规则

运行：

```bash
python tools/design_acceptance.py          # 人读报告
python tools/design_acceptance.py --gate   # CI 用，FAIL 退出码 1
python tools/design_acceptance.py --json   # 机器读
```

| ID | 规则 | 判据 | 等级 | 当前基线 |
|---|---|---|---|---|
| **R01** | 字号必须走令牌 | `font-size` 不得出现纯 px 字面量（`var()` / `clamp()` / `em` 不算违规） | 只拦新增 | 存量 **18** 条豁免 |
| **R02** | 不得引用未定义令牌 | `var(--x)` 的 `--x` 必须来自 CSS 定义、Vue `:style` 键或 JS `setProperty` | **零容忍** | **0** |
| **R03** | 禁色值兜底 | 不得写 `var(--x, #hex)`——兜底会静默掩盖令牌名写错 | 只拦新增 | 存量 **6** 条豁免 |
| **R04** | 间距落在栅格 | 主档 4 的倍数；微调档允许 2 的倍数；奇数（≠1px）违规 | 只拦新增 | 违规 **468** / 2244 声明 |
| **R05** | 配色令牌逐套覆写 | 16 个配色令牌必须在每个 `[data-skin]` 块出现 | **零容忍** | **0** 缺失 |
| **R06** | outline:none 需补偿 | 去掉 outline 的选择器须自带 `:focus`，或全局有 `:focus-visible` 兜底 | 观测（黄） | 未补偿 **24** 处，全局有兜底 |
| **R07** | transition ≤ 260ms | 超 `--motion-modal` 上限即违规（animation 另计，不设上限） | **零容忍** | **0** |
| **R08** | 尊重减少动效 | 必须存在 `@media (prefers-reduced-motion: reduce)` 覆写 | **零容忍** | **56** 块 |
| **R09** | hover 需配 focus | 有 `:hover` 的文件须有 `:focus` 规则 | 观测（黄） | 缺口 **22** 文件 |
| **R10** | 空/载/错三态齐全 | 每个存在的入口目录都具备三类语义 | **零容忍** | 两入口均齐全 |
| **R11** | 中性色色相同族 | `--bg` 与 `--ink` 色相差 ≤ 40°（仅当两者彩度都 < 0.04；任一方接近纯灰则豁免） | **零容忍** | **0** 套不同族 |

### 为什么 R06/R09 是「观测」而不是硬门禁

静态分析测不到**真实的键盘可达性**——focus 环可能由父级或全局提供，多数 `outline:none` 是
input 配合 border 变化的有意设计。把它们当硬门禁是假精确，只会训练人去加 `:focus-visible`
凑数。真正的判据在 §7 人工项（浏览器里逐元素 Tab 遍历）。

### 为什么 R05 只查 16 个配色令牌

`--scrim`（遮罩）、`--edge-w`（描边宽度）、`--r-*`（圆角）属于**结构令牌**，在 `:root:root:root`
给共享默认值、各皮肤共用，是有意的设计决定（黑遮罩在深浅两底上都正确下沉）。把它们计入
「必须逐套覆写」会产生 4 套皮肤 × 3 项的假缺口。**规则必须区分"有意共享"与"漏定义"。**

## 3. 基线机制：存量不背锅，增量不许破

一次把所有历史债清零不现实，但**允许新增**等于没有标准。所以：

- 存量违规写入 `tools/design_acceptance_baseline.json`（去重键集，不是行数）。
- 新增一条 → `--gate` 立刻红。
- 修掉存量后跑 `--update-baseline` 收紧白名单。

**防洗白**：`tests/test_design_acceptance.py` 里冻结了各规则的存量条数（`FROZEN`）。
想放宽任何一条，必须同时改基线文件和测试常量，让「多欠了一笔债」在 PR diff 里一眼可见。

## 4. 已用标准拦下的真实缺陷（v1.0 落地记录）

R02 零容忍在首次运行时就抓出一处：

| 位置 | 问题 | 后果 | 处置 |
|---|---|---|---|
| `workbench/components/MotionStatusBar.vue` | 3 处 `var(--line, rgba(255,255,255,.12))`，而 `--line` **从未定义** | 一直走白色半透明兜底 → 默认 zinc 浅色皮肤下**白线压白底**，chip 边界不可见 | 控件边界改 `var(--border-strong)`（1.4.11 的 3:1 档），分隔线改 `var(--border)`，去掉 `var(--surface, #1c1c1f)` 兜底 |

这正是商业化的典型失效：不是难看，是**控件失去可点击的视觉提示**。静态规则比人眼更早发现它。

### 5.4 配色色相：graphite 为什么"看着最怪"（2026-11-19 已修）

用户直接反馈「这套配色看着最怪」。量化后找到结构性原因，跟侧栏无关：

| 皮肤 | 底色 H | 文字 H | ΔH |
|---|---|---|---|
| zinc | 286.4° | 286.0° | **0.3°** 同族 |
| **graphite** | **268.2°** | **91.5°** | **176.7° 接近正互补** |
| paper | 88.0° | 55.9° | 32.1° 同族 |
| seed | 17.2° | 26.4° | 9.2° 同族 |

graphite 是四套里**唯一** bg/ink 色相差超过 32° 的一套，而且是接近正互补的 177°。
关键在于两者彩度都只有 0.008~0.010：**低彩度互补并置不会产生"温暖对比"，只会互相拉脏**
——底色显脏、文字显黄，整屏发闷。高彩度互补才是设计手法。

修法：`--ink` / `--text` 从 `#e8e6e0`（暖黄白 H91）改为 `#e6e9ef`（冷白 H250），
ΔH 降到 18°，亮度几乎不变（L .925 → .925），压 `--bg` 的对比度从 12.15 **升到 13.4:1**。
`skins.ts` 的色卡 `swatch` 同步更新。

这条已固化为 **R11**（静态判定，无需浏览器）：以后新增皮肤如果又写成低彩度互补，
门禁会直接红。变异测试覆盖两种情况——低彩度互补必须拦、高彩度互补不得误伤。

> 规则缺陷修正：初版 R11 对纯灰（C≈0）也做色相判定，而纯灰的色相是数值噪声
> （`#111111` 的 H 可以是任意值），会产生随机误报。现已在 C < 0.005 时豁免。

### 5.5 分隔线强度对齐业界（2026-11-19 已修）

侧栏与主区「看着糊在一起」，一开始被归因为亮度差不够。查了业界实际参数后，
两个结论都要修正：

| 项目 | 主区 | 侧栏 | 侧栏/主区 | 分隔线对比度 |
|---|---|---|---|---|
| GitHub Primer Dark | `#0D1117` | `#161B22` | 1.95× | **1.55:1** |
| VS Code Dark+ | `#1E1E1E` | `#252526` | 1.43× | **1.51:1** |
| DocMind graphite（修前） | `#16181d` | `#2b3037` | 3.18× | **1.21:1** |

**① 方向判断反了**：曾写「深色 UI 惯例是侧栏更暗」。实际 GitHub 的
`canvas-default`（主区 `#0D1117`）比 `canvas-subtle`（侧栏 `#161B22`）**更暗**，
VS Code 同样是侧栏更亮。我们的方向本来是对的，亮度比 3.18× 甚至比 GitHub 拉得更开。

**② 真正弱的是线**：`--border` 只有 7% 白（1.21:1），比业界弱约 25%。
现改为 13% / `--border-strong` 20%（约 1.48:1 / 1.87:1），与 VS Code 齐平且保有两档层次。
`--border-graphic` 38%（3.5:1，1.4.11 控件边界档）不变。

顺带印证 R11：GitHub 全套都是蓝调同族（bg H258 / border H252 / 文字 H243，跨度 15°），
我们修后是 bg H268 / 侧栏 H257 / 文字 H264，跨度 11°——比 GitHub 还收敛。

验证：A4 复测 **0/320**（分隔线加粗不影响文本采样）；轨道层次 6 状态全绿；20 条测试通过。

> **2026-11-20 修正：这个方向在产品型界面上不成立。** 「对齐 VS Code 1.51:1」是把
> 开发工具的标准套到了产品型 SaaS 上——GitHub / VS Code 是密集列表与代码块，必须靠硬边界
> 区分；现代产品型界面（Stripe / Linear / Notion）靠底色阶分区，边框淡到几乎不可见。
> 用户直接反馈「分隔太明显，市面上的其他产品已经很少这么做」。graphite 的 `--border`
> 已从 13% 回落到 8%，并改为「压深底色 + 淡边框」的组合，详见 §5.11。

### 5.6 强调色色相 207° → 222°（2026-11-19）

原 `--accent: #4dd0e1`（OKLCH H207）偏绿，在深底上接近"荧光青"，离工具类产品的观感较远。
业界对照：GitHub accent **H250**、VS Code **H245**，都是蓝。

但直接移到 245° 会与 `--bg`（H268）只差 **23°**，强调性反而下降——GitHub 是靠
把彩度提到 0.15 来补的。取 **222°**（与底色差 46°）：保留"青"的辨识度，又不像蓝那样通用。

改动只移色相、**L / C 全部不变**，逐色映射：

| 令牌 | 原值 | H222 | 对 `--bg` 对比度 |
|---|---|---|---|
| `--accent` | `#4dd0e1` | `#5accf0` | 9.58:1 |
| `--accent-deep` | `#79dce8` | `#80d8f6` | 11.05:1 |
| `--accent-text` | `#88d8e1` | `#8dd5ee` | 10.90:1 |
| `--tool` | `#278d9a` | `#328aa5` | 4.49:1（既存临界，非本次引入） |

`skins.ts` 的色卡 `swatch` 同步。验证：A4 **0/320**；门禁 PASS；20 条测试通过。

> **一个需要注意的事实**：这套设计里**没有统一品牌色**。四套皮肤的强调色相各异——
> zinc H186 / graphite H207→222 / paper H32 / seed H6。它们是"四套各自的性格"，
> 不是"同一个品牌色的四种明度"。所以改 graphite 的色相不影响其他三套，也不构成
> 不一致。若产品层面要做"看起来像同一个产品"，需要另立品牌色族工程，不在本标准的范围。

### 5.7 A1 字号层级收口（2026-11-19 已修）

原状：workbench 覆盖 90% 文本需 **5 个字号桶**（10.5 占 40.6% / 11 占 20.3% /
12 占 20.3% / 12.5 占 7.2% / 14 占 4.3%），ask 需 4~5 个。后四档只差 2px——
数字上"有 5 级"，观感上"没层级"。

**合并策略：小字往大并，可读性只升不降**（问答页以阅读为主，不适合反向压缩密度）。

| 页面 | 改动 | 合并后桶位 |
|---|---|---|
| workbench | `cap`/`micro` 10.5 → 11（并入 sm）；`md` 12 → 12.5（并入 body） | **11 / 12.5 / 14** |
| ask | `cap`/`micro` 11 → 12；`md` 13 → 14；`h3` 15 → 16 | **12 / 14 / 16** |
| seed（生成） | 生成器 `fs_cap=fs(12)`、`fs_md=fs(14)`，不再独立派生 | **12.9 / 15 / 16.1** |

每档仅 +0.5~1px（+4%~9%），密度变化温和。实测两页截图无溢出、无换行错乱。

**两个隐蔽的坑**（都是量具发现的，不是肉眼）：

1. **ask 页有一个逃出令牌体系的字号**：`AskSidebar.vue` 的 `.assistant-entry-main small`
   写死 `font-size: 11px`，占 6.3%，正是让 ask 卡在 4 桶的那一档。改回 `var(--fs-cap)`。
   这条同时让 R01 存量从 18 降到 17（基线已收紧，`FROZEN` 同步）。
2. **种子皮肤有独立字阶**：`skins-seed.css` 由 `tools/design_seed.py` 确定性生成，
   `fs_cap=fs(11)` / `fs_md=fs(13)` 各自派生 → 15 / 13.9 / 12.9 / 11.8 四个桶。
   不能手改生成物，改的是生成器的基准（`fs(12)` / `fs(14)`）；重新生成后
   diff 只有字号两行变化，其余逐字节不变。

验证：**A1 全通过（8/8 组合都是 3 桶）**；A4 **0/320**；门禁 PASS；20 条测试通过。

### 5.8 文件树分区行：白卡片改为轻底（2026-11-19 已修）

深色资源栏（`--ui2-rail-bg` 深墨绿）里，分区根目录行（`assets` / `behaviors` / `values`）
用的是 `background: var(--bg)` —— 浅色 palette 下 `--bg` 是 **oklch .972 近白**，
于是深侧栏里横着三条白纸。

代码里原本有一段补偿性设计，注释写得很清楚：

> 「分区卡是浅色底（var(--bg)），但深色资源栏把 --ink/--text 覆写成了白字，
> 直接继承会白字压浅底（实测 1.08:1）。这里把文本令牌复位回皮肤真实墨色 --mi-text」

也就是**为了防止白字压白底，把文字压成了暗色**。结果是白底 + 暗字，
外加彩色竖条 + 彩色文件夹 + 彩色标签，一行里四个元素在争同一个信息。
而且普通目录（`scenes`）是无底浅字，同一列表两种行样式，节奏断裂。

修法：底色改为 `color-mix(in srgb, var(--ui2-rail-text) 9%, transparent)`，
文字令牌回到 `--ui2-rail-text`。

| | 修前 | 修后 |
|---|---|---|
| 底色 | `var(--bg)` ≈ 白（对比 1:20） | 9% 亮底（对比约 1.3:1） |
| 文字 | 压暗到 `--mi-text` | 侧栏亮字 `--ui2-rail-text` |
| 分区标签 | 暗色，压在白底上 | 浅色（混向亮墨），约 **10.8:1** |
| 与普通目录行 | 样式不一致 | 接近一致，仅多一层轻底 |

保留"分区是一块"的分组意图，但把对比压到不抢注意力——和侧栏分隔线是同一条原则。
混合基色用 `--ui2-rail-text` 而非硬编码 `#fff`，四套皮肤自适应。

验证：A4 **0/320**（分区标签 10.8:1 远高于门槛）；门禁 PASS；20 条测试通过。

### 5.9 卡片与背景的层次（2026-11-19 已修）

「项目探索」卡片和主区背景几乎融在一起，只靠 1px 边框撑着。实测：

| | 修前 | 修后 |
|---|---|---|
| `--mi-bg`（页面底） | oklch **0.972** | oklch **0.955** |
| `--mi-surface`（卡片） | oklch 0.985 | 0.985（不变） |
| **差距** | **0.013（≈3 个 sRGB 阶）** | **0.030** |

下沉背景而不是提亮卡片——卡片 0.985 已接近白（1.0 是上限），再提没空间。
连带把 `bg-deep` / `hover` / `selected` 各下调 0.015~0.02，否则 `hover`(0.945)
与新的 `bg`(0.955) 只差 0.01，悬停几乎看不出来。

> **同时澄清一个容易搞错的事实**：工作台浅色**不走** `skins.css` 的 zinc。
> light palette 下 `palette.ts` 会 **移除 `data-skin`**，于是所有
> `:root:root:root[data-skin='zinc']` 规则全部失效，工作台实际用的是
> `memory-inspector-tokens.css` 的 `--mi-*` 浅色档。所以工作台的配色改动
> 要落在 `--mi-*` 上，改 `skins.css` 的 zinc 块对这个页面无效。
> （同一个组件还直接用了 `var(--mi-surface-level-2)` 当卡片底，绕过了皮肤层。）

另：原以为卡片"内部偏空"是 padding 或布局拉伸，实测**都不是**——卡片高 248px、
内容底 219px，下方空隙正好等于 `padding-bottom: 28px`，没有被拉伸。
偏空感来自 777px 宽的卡片装了少量内容，属内容密度问题，改 padding 只会更糟。

验证：A4 **0/320**；门禁 PASS；20 条测试通过。

### 5.10 A2 间距栅格收口（2026-11-19 已修）→ 达成 L2

**先修量具，再改代码**。浏览器端的合规判定原本用硬编码集合
`{2,6,10,14,18,22,28,30,36,44}`，漏了 26/34/38/42/46——那些合法偶数被算成违规。
统一为「偶数合规（2px 微调栅格），奇数只有 1px 合规」后，真实违规率从
26.5% / 13.9% 修正为 **22.4% / 10.1%**。

另修一处采样缺陷：`getComputedStyle` 会把 `margin: auto` 解析成实际像素
（如 505.28px），被当成"设计间距"误判。现只统计 ≤80px 的值。

**批量收敛**：静态扫描出 **787 处**奇数间距（7px×212 / 5px×201 / 9px×153 / 3px×113），
按「就近取 4 的倍数」一次改掉 **739 处**（单处最大变化 2px）：

| | 修前 | 修后 |
|---|---|---|
| workbench 渲染违规 | 22.4% | **0.3%**（1 处） |
| ask 渲染违规 | 10.1% | **0%** |
| 静态存量（R04） | 468 | **3** |

**视觉安全性靠差分证明**：同背景下两版截图逐像素比对，变化 **1.87%**，
且全部是**文字轮廓的 1px 位移**，无任何区块整体错位。门禁 PASS、20 条测试通过。

> **判据修正（原判据不适配本设计）**：v1.0 写的是「落在 8/16/32 三档 ≥ 70%」。
> 但这套 UI 的间距是 **2px 微调栅格**（常用值 8/4/12/6/10/16），实测三档占比只有
> 55%/58.7%。强行要求 70% 落在 8/16/32 会与既有设计语言冲突。
> 「留白成档」的本意是**值要收敛**，不是"必须是这三个值"，故改为
> **top6 覆盖 ≥ 80%**（实测 81.4% / 84.3%）。

## 6. 组合矩阵验收（L3 准入门槛）

四层正交意味着 **4 皮肤 × 1 造型 × 2 材质 × 5 布局 = 40 种组合**。

要求：**任取组合不得破相**。抽样规则：

1. 每套皮肤至少抽 2 种布局（默认 `fixed` + 差异最大的 `focus`）。
2. 切换后必查三处：遮罩是否下沉（不是发灰）、描边是否仍可见、强调色文字是否仍 ≥ 4.5:1。
3. 新增令牌必须确认 `skins.css` 有逐套覆写，否则会静默命中兜底——**看着没坏，其实没跟随皮肤**。

### 6.1 L3 实测（2026-11-20）

工具：`node tools/verify_l3_matrix.mjs`（`--all` 跑全 5 布局，`--shots` 存图）

| 维度 | 组合数 |
|---|---|
| 问答页：4 皮肤 × 5 布局 × 2 材质 | 40 |
| 工作台：2 调色板 × 5 布局 × 2 材质 | 20 |
| **合计** | **60，破相 0** |

每组判三件事：横向溢出、文本对比度（色值解析）、轨道层次。

**它抓到了单皮肤验收测不出的两个真缺陷**：

1. **玻璃材质把导航轨道玻璃化了**（24 组抽检里 10 组破相）
   `ask-glass.css` / `glass.css` 的「玻璃面」`:is()` 列表里带着 `.ask-side` / `.ft-panel`，
   玻璃底用 `--bg-raised`（白色）× 42% 透明 → 侧栏变浅；而侧栏文字是 `--ui2-rail-text`（亮白）
   → **白字压白底，实测 1.02:1**，seed 皮肤 10 处文本不可读，导航全废。
   深色轨道 + 浅色页面这个组合下玻璃化必然牺牲可读性（要 ≥90% 不透明才过 4.5，那就不是玻璃了），
   所以**导航轨道不参与玻璃**，三处（玻璃面 / 底层 / 降级）都把侧栏移出了列表。

2. **`.new-chat` 漏了 `--btn-fill` 声明**（4 组残留）
   `glass.css` 有一条逃生口约定：填色按钮必须声明 `--btn-fill`，否则玻璃会把底换成半透白，
   深色字压浅底 → **1.43~1.54:1**。注释里写着"已修 4 个隐形按钮，含问答页「新对话」"，
   但那一处实际漏了。补上后归零。

> **量具教训**：glass 材质下容器背景是半透明的，`getComputedStyle().backgroundColor` 会返回
> `rgba(...,0)`，直接算亮度得 0 → 10 组 glass 全被误判成"侧栏 Δ≈-0.03"。
> 层次判定必须**向上找第一个不透明祖先**，和对比度的背景解析同一套逻辑。

### 6.2 边框淡化 + 色阶分区（2026-11-20）

用户反馈「分隔太明显，市面上的其他产品已经很少这么做」。查证后确认这是方向问题：
§5.5 用开发工具（GitHub 1.55 / VS Code 1.51）的边界强度做参照，而 DocMind 是产品型 SaaS。

**但边框不能单独调淡**——卡片原本**完全靠边框存在**：zinc 的 `--surface`(#ffffff) 与
`--bg`(#fcfcfd) 只差 3 个 sRGB 阶。边框一淡，卡片整片消失。现代产品的做法是
**弱边框 + 明确的底色阶差**，两者必须一起改。

| 皮肤 | 底色 | 卡片 | 阶差 | 边框对比度 |
|---|---|---|---|---|
| zinc | `#fcfcfd` → **`#f4f5f7`** | `#ffffff` | 3 → **11 阶** | 1.31 → **1.10:1** |
| graphite | `#16181d` → **`#101319`** | `#1c1f26` | — | 13% → **8%** |
| seed（生成） | `bg_l` 0.975~0.99 → **0.945~0.96** | `surface` 偏移 +0.008 → **+0.045** | 2 → **11 阶** | 同步淡化 |
| paper | **不动** | — | — | 墨边 #14110f 是 brutalist 骨架，不属于「太明显」 |

除边框外不动别的东西：控件边界仍走 `--border-graphic`（≥3:1，1.4.11 要求）。

> 调 seed 时先试过 `bg_l` 0.93 起步，实测背景灰得发闷（整屏压暗），
> 与 zinc 的观感不一致，上收到 0.945。**这类"压深底色"的改动必须在真实截图上看一眼**，
> 数字上"阶差 11 阶"成立不代表观感成立。

验证：L3 **60 组 0 破相**；A4 **0/320**（各皮肤最低对比 5.24~5.59，比改动前还高，
因为文字压在更深的底色上）；A1/A2 无回归；门禁 PASS。

### 6.3 主区建议项改为裸列表（2026-11-20）

背景压深后暴露出另一处不对等：左侧三个建议项是**卡片**，右侧「当前工作区」是**裸列表**，
同一屏两种组织方式。改为统一裸列表。

**发现：裸列表样式早就写好了，只是被覆盖了。**
`shared/ui-v2.css` 里已有一套完整实现——`display: grid; grid-template-columns: 28px 20px 1fr auto`、
`::before` 生成序号 `01/02/03`、底边细线、hover 底边变强调色且箭头右移，
DOM 结构也完全对应。但 `AskApp.vue` 的 scoped 样式又把它盖回了卡片
（`border: 1px` + `border-radius` + `gap: 8px`），且两者特异性相同、组件后加载。
所以这次**没有新写样式**，只是撤掉那层覆盖。

> **连带教训：淡化边框不能一刀切。** 撤掉卡片后，三行之间几乎看不见分隔——因为
> 列表线用的是由 `--border` 派生的 `--ui2-line`，而 `--border` 刚被淡到 1.10:1。
> 不同用途的线需要不同强度：
>
> | 用途 | 令牌 | 强度 | 理由 |
> |---|---|---|---|
> | 容器边框 | `--border` | ≈1.10:1 | 只作结构提示，卡片靠色阶成立 |
> | **列表分隔线** | `--ui2-list-rule` | **≈1.18:1** | 承担"分隔"职责，太淡会让行糊在一起 |
> | 控件边界 | `--border-graphic` | ≥3:1 | 1.4.11 硬要求 |

验证：L3 **60 组 0 破相**；A1 **3 桶**（序号用 `--fs-cap` 未打破层级）；A2 0.3%/0%；
A4 **0/320**；门禁 PASS。

### 6.4 空状态垂直居中（2026-11-20）

卡片改裸列表后，主区「输入框以下」露出半屏空白。让整组（标题 + 建议 + 输入框）
合理分配视口高度。**这件小事试了五次才对**：

| 尝试 | 结果 |
|---|---|
| ① `flex: 0 0 auto` | 内容堆在顶部（原状态） |
| ② `flex: 1 1 auto` + 子项 `margin: auto` | main 剩余 212px 就是不分给 `flex-grow` |
| ③ `display: contents` 改正常盒子 | stage 只撑到内容高 630px，仍不吸收 |
| ④ `min-height: calc(100dvh - 58px)` + 居中 | 1440×900 成立，**1440×473 输入框压到建议列表上**（用户截图报的） |
| **⑤ stage 接管滚动 + chat-col `margin: auto`** | **成立** |

**最终方案**：

```css
.ask-main.is-empty { overflow: hidden; }                       /* 滚动权下放 */
.is-empty .chat-stage { flex: 1 1 auto; min-height: 0; overflow-y: auto; }
.is-empty .chat-col.is-welcome { flex: 0 0 auto; margin: auto; }
```

stage 撑满「顶栏与输入框之间」，chat-col 在其中 `margin: auto` 居中。
空间不足时 stage 内部滚动，**输入框常驻底部**（内容再多也不会被挤走）。

**三条教训**：

1. **必须测矮视口**。前四版都在 1440×900 / 620 下验证通过，1440×473 直接重叠。
   现在 `tools/verify_l3_matrix.mjs` 之外另有几何重叠检测覆盖 900/620/473/400 四档高度。
2. **`min-height` 不能卡「视口减顶栏」**。第 ④ 版忘了扣输入框的 208px，
   大视口反而多出 212px 滚动条。
3. **几何重叠检测会误报**。stage 有 `overflow-y: auto` 时，滚动区内的元素与外部元素
   在 `getBoundingClientRect` 上相交，但视觉上被裁剪 —— 必须配合截图确认。

验证：四档高度（900/620/473/400）均无重叠、无外层滚动；A1 3 桶 / A2 0.3%·0% /
A4 **0/320**；L3 **60 组 0 破相**；门禁 PASS。

> **连带发现一个既存缺陷**：居中把原本在视口外的元素推进了 A4 采样范围，
> paper 皮肤右侧栏「资料 / 模型」标签的 `--text-muted`(#6b6356) 压在
> `--surface`(#f3f1ea) 上只有 **4.42:1** —— 一直超标，只是以前没被采到。
>
> 修的时候踩了第二个坑：改到 `#665f52`（理论 5.0:1）实测只有 **4.58**。
> A4 的截图采样取的是**抗锯齿中间像素，比精确色值偏亮约 0.4**。
> 最终降到 `#5c5547`（理论 5.6），实测 **5.25**，留出冗余。
> **改临界对比度不能按理论值卡线，要按「目标 − 0.4」反推理论值。**
