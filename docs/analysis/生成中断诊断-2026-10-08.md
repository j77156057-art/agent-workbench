# 「模型生成中断」系统性诊断报告

日期：2026-10-08 ｜ 版本：DocMind 0.1.0-beta.1
数据源：`.docmind_traces.jsonl`（4,492 条 trace，4.1 MB）

---

## 0. 结论速览

用户报告的现象是「每次回答都在生成到一半时被中断（约 5–6 秒结束）」。经全量 trace 取证，
**这不是中断，是"快速结束"**：模型在 5–6 秒内正常答完并主动收尾。

三条被证伪的假设：

| # | 假设 | 证据 | 结论 |
|---|------|------|------|
| 1 | `max_tokens` 耗尽导致截断 | `finish_reason == "length"` 的记录数 = **0** | ❌ 排除 |
| 2 | 流式超时 / 连接断开 | `TURN_DEADLINE_S = 0`（不限）、`LLM_TIMEOUT = 180s` 均未被命中 | ❌ 排除 |
| 3 | 上下文超长被截断 | 实测 `prompt_tokens` 最高 295,074，窗口 1,048,576 | ❌ 排除 |

真正的现象：**上游返回快、模型也答得快，5–6 秒是正常完成时间**，不是被切断。

## 1. 用户指出的三个问题与修复

### 问题 1：deepseek-flash（1M 上下文）只给 43k 输出空间

**根因是两层叠加的 bug：**

```python
# 1) _MODEL_CONTEXT_OVERRIDES 里没有 deepseek-flash 条目
#    → 落到 _PROVIDER_CONTEXT_DEFAULT["deepseek"] = 131,072
# 2) OUTPUT_TOKEN_MAX = 65,536 的全局硬顶
#    131,072 × 0.33 = 43,253  ← 用户看到的 4.3 万
```

注意 `_MODEL_CONTEXT_OVERRIDES` 是**按插入顺序首次匹配**的 dict，所以
`deepseek-flash` 必须排在 `reasoner` 之类通用键**之前**。

**修复：**

```python
_MODEL_CONTEXT_OVERRIDES = {
    ("deepseek", "deepseek-flash"): 1048576,      # 新增
    ("deepseek", "deepseek-v4-flash"): 1048576,   # 新增
    ("deepseek", "reasoner"): 65536,
    ...
}
OUTPUT_TOKEN_MAX = int(os.getenv("DOCMIND_OUTPUT_MAX_TOKENS", "0"))  # 0 = 不设硬顶
```

`output_token_budget()` 改为仅在 `OUTPUT_TOKEN_MAX > 0` 时才套用上限；
`prompt_token_budget()` 的预留量从硬编码 `LLM_MAX_TOKENS + 512` 改为读模型的
**真实** output 预算。

**效果（8.0 倍）：**

| | 窗口 | prompt 预算 | output 预算 |
|---|---|---|---|
| 改前 | 131,072 | 98,304 | **43,253** |
| 改后 | 1,048,576 | 702,034 | **346,030** |

且两层不变式 `prompt + output ≤ window` 仍然成立（1,048,064 ≤ 1,048,576）。

### 问题 2：5–6 秒结束 ≠ 超时

确认无超时：`TURN_DEADLINE_S = 0` 与 `LLM_TIMEOUT = 180` 在整个 trace 集里从未触发。

最后一轮实测：`question_chars=2`，`prompt_tokens=106,348`，`llm_ms=5,118`，`completion_tokens=454`
——提问很短、回答也短，5.1 秒是**正常的生成耗时**。所谓"中断"实际是
**任务在第一步就收尾了**，而非被外部切断。

### 问题 3：工具调用与重试次数默认全部放开

原实现有两处隐蔽的限制：

```python
# 1) _execution_policy 静默把用户值夹到 20，且把 0 当作"未设置"
# 2) 迭代硬上限里 nudge 项被无条件计入 slack，
#    导致 max_nudges=0 时上限被"收窄"成 tool_step_limit + 7
```

**修复：**

```python
def _execution_policy(self):
    """返回 (max_nudges, max_final_continuations)。**0 = 不限**。"""
    return _read("max_nudges"), _read("max_final_continuations")

@staticmethod
def _limit_ok(used, limit):
    if not limit or limit <= 0:   # 0/None = 不限
        return True
    return used < limit
```

迭代上限只在限额**显式为正值**时才计入 nudge slack：

```python
if tool_step_limit > 0:
    _slack = _MAX_FORCED_FINALS + 4 + NAV_FREE_STEPS
    if max_nudges > 0:
        _slack += max_nudges
    if max_final_continuations > 0:
        _slack += max_final_continuations
```

六项容量设置默认全部归零（`agent_runtime/capacity.py::DEFAULTS`）：

| 设置项 | 改前默认 | 改后默认 |
|---|---|---|
| `max_agents` | 0 | 0 |
| `main_max_steps` | 0 | 0 |
| `child_max_steps` | 0 | 0 |
| `max_nudges` | **2** | **0（不限）** |
| `max_final_continuations` | **2** | **0（不限）** |
| `task_token_budget` | 0 | 0 |

校验上界从 20 放宽到 1000（与 `main_max_steps` 对齐），前端 `SettingsView.vue`
同步放开 `max=1000` 并标注「0 = 不限」。

**保留的护栏**（与步数无关，防的是"原地空转"而非"多跑几步"）：
`_MAX_FORMAT_STALLS`、重复调用拦截、失败熔断。

## 2. 故障分布的真相

真正落盘进 trace 的 outcome 分布（去掉测试夹具后 2,154 条）：

| outcome | 占比 |
|---|---|
| `completed` | 70.0% |
| `evidence_fallback` | 20.1% |
| `verbatim` | 4.5% |
| `empty` | 1.5% |
| `failed` | 1.4% |
| `fallback_cleaned` | 1.0% |
| `format_stall` | 0.6% |

### 2.1 `web_search` 40% 失败率是**虚的**

原始统计：105 失败 / 265 调用 = 40%。**但 78 条是测试夹具**：

- `session_id == "ephemeral"` 且 `latency_ms == 0` → 一条网络请求都没发；
- `obs_chars == 7` 出现 58 次，对应 `agent.py:5156` 的**子代理白名单拒绝**文案
  `[受限] 本子代理只允许使用：…，已拒绝。`（可见字数恰为 7）；
  对联开关文案长 124 字符，**不是**同一个。

剩下 27 条真实失败中，**25 条 `outcome` 仍为 `completed`**——搜索失败并不会让整轮任务失败，
模型会自己换关键词或改用本地工具。

**真实失败率 = 27 / 214 = 12.6%**，且集中在 5.0s（单次搜索超时）与 10–12s（两次超时叠加）。

### 2.2 `failed` 的 316 次是测试夹具

`RuntimeError: 模型调用炸了` × 316 是测试里的固定字符串。真实信号是
`APIConnectionError: Connection error.`（127s）。

### 2.3 唯一真实的输出耗尽案例

`qwen3.6:35b-a3b-agent256k`（ollama）：`completion_tokens=67246` 撞上旧的
`OUTPUT_TOKEN_MAX`，`llm_ms=1,311,628`（21.8 分钟），随后
`AttributeError: 'NoneType' object has no attribute 'peek'`。
这条已被问题 1 的修复解除（硬顶取消）。

## 3. `empty` 归因修复（本轮新增）

原代码无论本轮有无工具失败，首句都写死：

> 「**这多半不是你的问题写得不清楚**，而是上游/中转返回了空内容（瞬时故障），直接重试通常就能拿到。」

真实故障链是「工具一直报错 → 模型拿不到信息 → 放弃作答」。此时让用户重试是**错误方向**。

改成互斥两支：

```python
if fail_total:
    # 工具报错 → 模型放弃 → 空
    # 「最可能的原因就在这里」…「单纯重试大概率无效」
else:
    # 本轮无工具失败，才轮到「上游回了个空信封（瞬时故障）」
```

新增 `EmptyResponseAttributionTests` 4 条钉子锁死该不变量。

## 4. 需要补充的信息（若问题复现）

1. **完整对话轮次的 trace 记录**——`turn_id` 与 `session_id`；
2. **前端收到的 SSE 原始事件序列**——确认是 `final` 还是中途 `error`；
3. **上游返回体的 `finish_reason`**——`stop` / `length` / `tool_calls` 三者含义完全不同；
4. **provider 侧账单/限流记录**——排除 403/429。

排查优先级：① `finish_reason` → ② 工具失败链 → ③ 上下文用量 → ④ 前端渲染。
