## 3. 两个结论

### ① 你的说法「差异全部落在侧栏」—— 一半对

**侧栏确实最集中**（ask 37.8% / ask-zinc 56.5%），但**主对话区另有显著占比**
（ask 44.3% / ask-zinc 26.5%）。不是「全部在侧栏」。

### ② 主对话区那 44% —— **本节结论已证伪，保留仅供追溯**

> ⚠️ **2026-10-09 更正（前端 agent 用错位重比证伪）**：
> 本节原判断「侧栏模型名变短 → 块变矮 → 对话区整体位移」是**错的**。
> 错位重比（当前截图相对基线平移 `dy ∈ [-24, 24]` 再逐像素比）显示
> 三条曲线最低点都在 **dy=0**，平移只会更差，**塌掉 0.0%**。
> 即差异不是位移。
>
> 真实原因见下面第 9 节。本节保留原文，是为了让「我曾据均匀分布的错统计
> 推出过一个错结论」这件事可查 —— 删掉它就等于掩盖证据链。

（原文）侧栏「运行状态」块的模型名从

```
qwen3.6:35b-a3b-agent25 + 6k   →   qwen3.6:35b-a3b-agent256k
```

字符串变短，**那一块的高度会变**。若它变矮，下方的主对话区整体上移，
则该区**每一行内容都错位**，于是整片都被标成差异。

这与观测吻合：主对话区的占比是**分散在多条带上的连续量**（44.3% 摊在
3–4 条带），而非集中在某一两句文本上。

## 4. ⚠ 因此 `--update` 暫时不该做

理由不是「基线旧了」，而是：

**如果主对话区那 44% 是侧栏字符串引起的连锁位移**，那么 update 会把这个
位移定成新基线。后果是**下次任何人改侧栏任何一个字，都会再次引发全对话区
位移**，视觉回归反复红 —— 它的报警价值就被这次 update 消耗掉了。

## 5. 需要你先确认两件事

### ① 侧栏模型名这个变化是预期效果吗？

如果是（模型名短了是 capacity 那批的预期），那侧栏 37.8%/56.5% 的差异
**是合理回归，可以进基线**。

### ② 主对话区的位移是预期还是意外？

判别方法（我可以做，约 10 分钟）：把 diff 图的对话区与基线图**错位 N 像素
后重比对**，若差异大幅下降，就是位移；若不变，是真实内容变化。

**我倾向先做 ② 再 update** —— 因为「合理位移」和「意外内容变化」对基线的
含义完全不同，而 update 是一次性的，烧错了要再找回来得靠 git。

# 9. 后端补充：真实根因与一个疑似真 bug

**上面 1–8 节的结论已被前端 agent 证伪**（错位重比，见第 2 节②的更正框）。
下面是核实后的根因，记在这里以免后人照着错的那版做判断。

## 9.1 不是位移，也不是「模型名变短」

错位重比（`dy ∈ [-24, 24]`，全页/侧栏/主对话区三条曲线）**最低点都在 dy=0**，
平移只会更差、塌掉 0.0%。位移假说证伪。

实际渲染对比：

| | 基线 | 现在 |
|---|---|---|
| 资料文档 | 3 篇 | **0 篇 / 尚未上传文档** |
| 模型 | `qwen3.6:35b-a3b-agent25` | **未配置** |
| 显存 | 6.1 GB | **—** |

**差异不是「内容变了」，是「内容整块没了」。**

## 9.2 根因：夹具不封闭

`verify_scene_canvas.py:276-294` 的夹具用 uvicorn 跑**真的 `api.py`**，
但只隔离了 `code_root` 与 `STATE_FILE`：

* 知识库上传列表
* 运行时模型配置
* 显存

**都没有隔离，是从这台机器的真实状态漏进画面的。** 基线里那 3 篇文档和
那个模型名就是这么来的；现在它们空了，像素就红一片。

**所以我上一轮把红归因给「capacity 改了模型名」也是猜的，收回。**

## 9.3 连带发现：很可能是真 bug

探针显示开机**只发了 `/api/health` 一个请求**；`/api/config`、`/api/projects`、
`/api/model_status` **一个都没发**，且**没有任何报错或提示条**。

`useModelConfig.ts:50-52` 的 catch 是**静默的** —— 加载失败不告知用户。

**这既是基线不稳的原因，也很可能是真 bug**：界面安静地显示「未配置」
而不说为什么。用户看到的是「我的模型没配」，实际可能是「配置请求没发出去」。

## 9.4 因此 `--update` 更不该做

位移至少还是**同一份内容挪了位置**；而「问答页开机拿不到任何配置」
这个降级状态若被定成期望图，那么**将来任何一台机器上配置正常加载，
视觉回归就会红** —— 而且方向相反：是「正常」被「降级」判成回归。

## 9.5 后端侧清查结论（排除后端嫌疑）

为钉死「开机只发 `/api/health`」是不是后端问题，起了**与夹具同规格**的
服务器（真实 `api.py`、隔离 STATE_FILE）冷启动探测：

| 端点 | 首屏 | 稳态 |
|---|---|---|
| `/api/config` | 2064 ms | **8 ms** |
| `/api/model_status` | 2077 ms | **2084 ms** ← 恒定 |
| `/api/projects` | 8 ms | 3 ms |
| `/api/agent-capacity` | 3 ms | — |

**四个端点全部 200 —— 后端不是瓶颈，也没有拦着不发。**

那 2 秒已定性，**不是代码问题**：

```
socket.create_connection(("127.0.0.1", 11434))
  -> ConnectionRefusedError  2051ms
```

**裸 socket 连本机一个关闭端口，在这台 Windows 上要 2 秒**（不是常见的
<10ms）。`NO_PROXY` 已含 `127.0.0.1`，与代理无关。`api.py:4465` 的注释
早就记过同一现象（2035ms）。

`/api/model_status` 恒定 2 秒是因为它每次都要 `_ollama_ps()`；Ollama 当时
没运行，于是每次都撞上这 2 秒。**Ollama 跑着时应该是毫秒级。**

### 因此 bug 归属前端

后端答得上、最慢 2 秒且原因明确，那么「一个都没发」只剩两种可能，
**都在前端**：

| 可能 | 说明 |
|---|---|
| 并发发多个请求，慢的那个导致整体被放弃 | 若有并发/超时逻辑 |
| 逻辑分支没走到，根本没发 | 与「静默 catch」并存时最像这个 |

**建议查的方向**：`useModelConfig.ts:50-52` 的静默 catch 只是**吞掉症状**，
真正的问是「为什么没发」。在没发的状态下 catch 永远不会触发 —— 所以
那三行 catch 可能根本不是这条 bug 的位置。
