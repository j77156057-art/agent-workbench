# `tool_search` 的匹配缺陷：精确名可能返回别的工具，且零测试覆盖

> 立档日期：**2026-10-08**。发现于补全工具披露时顺带实测
> （见 `docs/known-defect-tool-visibility-and-dual-text.md` §2c）。
>
> ⚠ **§2 的实测表是「补全修复之前」的状态，现在已不复现。**
> 那三行里 `web_weather` / `dev_patch` 两项的根因是 `_tool_blocks()` 缺补全
> （已在同笔修掉，见那篇 §2c）。**本文记录的是剩下那部分**：
> `dev_mcp_add → dev_mcp_search` 那种**精确名命中别的工具**的行为，
> 以及「`tool_search` 零测试覆盖」这个事实本身。

## 1. 一句话

`tool_search` 是 progressive 按需披露模式的**唯一检索通道**，
它的匹配是**子串**，精确名在名字里匹配不上时会退到**说明全文**匹配 ——
而说明里常常提到别的工具名，于是可能返回**另一个工具**的用法，
且返回格式与正确情况**完全一样**，没有「这是模糊匹配」的标记。

`git grep -l tool_search -- tests/` **零命中**：它没有任何测试。

## 2. 实测历史

| 查询 | 补全修复前返回 | 现在 |
|---|---|---|
| `web_weather` | 「没有匹配「web_weather」的工具」 | ✅ 自己的用法 |
| `dev_patch` | `dev_diagnostics(...)` 的用法 | ✅ 自己的用法 |
| `dev_mcp_add` | `dev_mcp_search(query): 按领域或能力词…` | ✅ 自己的用法 |

**当前状态下三例都已正确** —— 因为精确名现在能直接命中 ①（`blocks` 里有了）。
但 ① 依赖「query 是名字的子串」，而 ② 那条路**依然会返回别的工具**：

```python
hits = [n for n in blocks if query in n.lower()]            # ① 名字子串
if not hits:
    hits = [n for n in blocks if query in blocks[n].lower()]  # ② 全文子串
```

② 是**兜底**，任何不在名字里的查询都会走到它，而 `blocks[n]` 是完整说明，
说明里经常出现别的工具名。**所以缺陷没有被消除，只是被 §2b 的补全掩盖了。**

## 3. 为什么这比「查不到」更糟

「查不到」是**响亮失败** —— 模型会说「没有这个工具」，用户看得见。

返回**别的工具**的用法是**静默失败**：
* 模型拿到的参数格式是真的（那确实是某个工具的合法格式）
* 但与它想调的工具无关
* 于是它可能照着 `dev_mcp_search` 的格式去调 `dev_mcp_add`，参数对不上
* 护栏只拦「没授权」，不拦「参数格式错」—— 所以它会真的发出去

这与本轮反复出现的那族是同一类：**失败时没有声音**。

## 4. 建议的修法（**未做**，需真跑验证）

1. **精确名优先**：`blocks.get(query)` 命中就直接返回它，不看别的。
2. **子串命中要标注**：返回里说清「按模糊匹配找到以下 N 个」，
   并把精确名排在最前（现在靠 dict 顺序，不靠精确度）。
3. **description 匹配显式降权**：②的结果标注「仅按说明文本匹配」——
   它不构成「你要找的工具」。
4. **补测试**：至少断言「用任一精确工具名查，返回的第一个必须是自己」。
